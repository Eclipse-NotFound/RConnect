# 源时钟校准必须同步换算播放位置

> 2026-10-07后续核对：本实验之后，0.2.18-dev/04438276已完成14组1648/0、最终旧905负控与正常无驱动eb84c49f11并部署。最新状态见[state/deployment-m46-2026-10-07.md](../../state/deployment-m46-2026-10-07.md)。下文的未部署/待验证语句描述当时阶段，原失败和因果边界保留。


此结论只描述RConnect自有RemoteMotion，不是原版游戏引擎机制；留在本模组。

## 已确认的算法缺口

RemoteMotion保存对方源时间的播放游标cursor；offset将本机接收时间换算到对方时钟。首次交接可能先收到旧帧，较新的到达会降低offset。原实现只修改offset，没有同步cursor。在多次小幅改善（每次199ms，低于250ms的单次重置门槛）后，期望播放位置累计前移，实际游标却仍留在旧时间。原10%速度修正来不及补偿累计差异。

R2的固定反例：0..3000ms的16份源历史帧，200ms间隔；在本机1000..1015ms连续接收，之后50ms正常收包、10ms采样。坐标恒定，不触发传送，源和接收时钟各自单调。最新包在1015ms已有轻机枪和新光晕；1500ms后仍返回2800ms源帧的空武器/旧光晕。R2查询副本记录cursor1566.5、offset−1985、delay100、期望4400；新流直接以同一末帧开始时正常。

root随后用当前真实类、无查询方法重复同一输入，并另加严格接收顺序采样；两种顺序都失败。逐步减至2–16帧的同一族反例，首次9帧仍在1500ms时显示旧武器；8帧及以下通过。这只是该时序族的最小帧数，不保证所有参数空间全局最小。

## 排除对照与修正

| 隔离回放 | 实際变化 | PASS / FAIL |
|---|---|---:|
| clock-original-01 | 原真实类，17项首版测试 | 15 / 2 |
| clock-original-02 | 原真实类，最终18项测试 | 15 / 3 |
| clock-delay-01 | 仅实验副本固定缓冲为100ms | 15 / 3 |
| clock-compensated-01 | 仅实验副本同步补偿cursor | 18 / 0 |
| clock-shared-01 | 实际合入后的共享生产类 | 18 / 0 |

最终四组测试源码相同，没有延长1500ms、降低颜色条件或改检查门槛。固定缓冲仍红，说明缩短缓冲不足以解决这个反例。严格单调采样仍红，说明原回放的固定采样时刻不是这个缺口的必要前提。

修正在原offset校准处加入：

```as3
var previousOffset:Number=offset;
offset=Math.min(offset,clockOffset);
cursor+=previousOffset-offset;
```

同量换算保持播放位置与新时钟映射一致。没有修改延迟计算、队列上限、TTL、插值速度、暂停裁决、传送阈值或无时间戳路径。原offset大步重置分支仍在。共享实际类与补偿实验类逐字节一致；原类指纹对应保留2c83候选的源manifest。正反回放均正常退出，失败不是崩溃。

18项还覆盖：普通抖动期间有限位置/不超收到端点/不倒退/不突跳、收到末帧后到达端点、忽略旧帧、原传送尺寸门槛、暂停收齐最后在途快照/不外推/恢复不倒播、无时间戳端点插值与settle。不是所有网络分布或长运行的穷举。
