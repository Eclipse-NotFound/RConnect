# RConnect 双侧同步机制审查

2026-10-10。结论：已经出现明显的结构性负担，值得安排一次专项整理。主要问题是同一对象的时序、状态与退出清理分属多个路径，旧路径没有完整退场；传输层、房间归属交接和原生显示适配仍有保留价值。

本轮只审查和记录，没有修改运行代码、编译、启动游戏或部署。下列结构判断、静态可证问题、既有实测证据分别标明。

## 当前真正的数据流

“宿主权威”不足以完整描述现有实现：

| 对象/结果 | 谁决定 | 如何传递 |
|---|---|---|
| 同房敌人 AI、死亡、掉落和场景结果 | 宿主 | 约 200ms 的 unitsync；加入侧冻结原生 AI，重放画面 |
| 双方分房时的敌人和场景 | 所在房间的玩家端；宿主管理归属记录 | 换房时 seal → ready → grant → ack，提交完整房间状态 |
| 自己的移动、瞄准和玩家身体 | 自己 | 默认 50ms 的 playerstate/worldstate；对方显示缓冲后的化身 |
| 加入側对同房敌人的伤害 | 加入侧先用原生减伤算净损失；宿主应用净损失、负责结果 | MirrorHitUnit → 生命/护甲/护盾差额 → damage；宿主用 D_INSIDE 避免再次减伤 |
| 敌人对远端玩家、队友伤害 | 攻击所在端检测命中；受害玩家所在端执行其原生减伤 | RemoteDamageUnit / PeerHitUnit → NativeHit |
| 抓取、掉落、门箱、破墙、探索、暂停 | 各自协议维护归属、预测或回执 | 与上述快照并行，部分借用玩家高频包 |

~~~mermaid
flowchart LR
    Native["房间归属端：原生模拟"] --> Capture["采集单位、武器、场景状态"]
    Capture --> Wire["Session / TCP"]
    Wire --> Logic["接收：当前逻辑状态与回执"]
    Wire --> Motion["接收：显示缓冲"]
    Logic --> Proxy["原生受击代理"]
    Motion --> View["位置、身体、武器、特效"]
    Proxy --> Reports["命中与交互上报"]
    Reports --> Wire
    Room["RoomSync：房间归属与交接"] --> Logic
    Room --> Native
~~~

这是职责图，不表示所有箭头都对应单一函数。最重要的区别是：战斗结果的时效与画面缓冲的时效不同，整理时必须保留这一区别。

## 行为与现有要求（Spec / 可观察正确性）

这里有 2 项需要后续验证/修正的具体问题。它们与结构发现可能共享证据，不能把 6+2 解读为 8 个独立已复现故障。

**B1 — 高优先级：没有发送消费者时，已结束弹道缺少清理条件。静态调用链可证，尚未做长局内存实测。**

[GameBridge:294](../src/rconnect/game/GameBridge.as:294) 在非镜像房间持续 observe 敌人，并观察玩家武器；没有“本数据是否需要发送”的门控。[UnitPresentation:134](../src/rconnect/game/UnitPresentation.as:134) 创建 endSentAt=0 的 recorded 事件，:175 只有“已结束且已发送结束状态，再过 700ms”才清理；:196 的发送标记只在 capture 中写入。

两条正常场景会没有这个 capture：
1. 离线游玩：Session 不发玩家/单位快照，观察回调继续运行。
2. 加入侧独房战斗：本地运行敌人，但 Session 的 CONNECTED 分支只定期采集自己；敌人完整状态主要到房间交接 checkpoint 才采集。

保持同一把武器持续开火时，事件数组保留已结束 Bullet 的引用与帧历史，并继续遍历；每条最多 64 帧并不限制事件总数。后果是内存、扫描量及后续交接打包负担随历史积累。是否达到可见卡顿或消息大小上限，本轮未测量。它也不能直接解释此前同房压力测试的全部失败。

该条件在 dcef118/22 中已存在（玩家和部分特殊弹 recorded）；23 将所有被观察弹道设为 recorded，扩大了涉及范围。建议首先让采集跟随实际订阅范围启停，并为无消费者/断开/换房设置明确退役规则。有消费者时仍须保证未发送的末帧不被过早丢弃，不能简单删除 endSentAt 保护。退出后的遮罩归还等必要收尾仍需执行，不能将全部离线回调一并停掉。

**B2 — 中高优先级：敌人的身体/枪械仍混用接收时刻与缓冲后的源时刻。代码路径已确认，具体视觉偏差尚未新增实测。**

用户反复反馈“敌人攻击动画卡顿”“弹道与枪口对不上”以及 SATS 停止错位。现在玩家路径大体共用源时间，但敌人路径尚未完整统一：

- [GameBridge:5745](../src/rconnect/game/GameBridge.as:5745) 的敌人缓冲只放 x/y/bodyEffects。RemoteMotion(200) 使用带缓冲的源时间，ProjectileVisuals:139 也按它播放弹道。
- [UnitPresentation:228](../src/rconnect/game/UnitPresentation.as:228) 收到快照就切换姿态；:281 用累计开火数新增本地队列；:283 用 getTimer 创建新的武器过渡。
- [UnitPresentation:320](../src/rconnect/game/UnitPresentation.as:320) 的枪械位置、开火、准备/换弹计时按本机收包后的时间推进；RConnectAnimationAccess:78 的位图动画按本地帧推进。

因此同一源快照的“敌人位置/弹道”和“转身/枪口开火”能落在不同播放时点。收包成批或暂停恢复时，两者需要更多补偿。建议在显示层为同一个敌人统一取样位置、姿态、武器和事件；血量、权限、抓取同意等逻辑状态仍按当前状态处理，不能一起延迟。

现有正常帧与暂停专项通过，不能证明这些时点天然一致；本项不宣称所有相关用户问题都由此单独造成。

## 哪些复杂度应保留

- RoomSync 的冻结、冲刷未结算请求、交接世代和确认流程，是分房后不回血、不复活、不重复掉落的基础。它只有 380 行，流程相对集中；应整理接口，保留语义。
- roomEpoch / roomKey / roomTerm 分别隔离地图实例、房间和归属交接。丢掉其中一项会使迟到包重新污染当前房间。
- 玩家受害端减伤与敌人净损失上报的差异，是现有伤害规则；不能把净损失改当原始伤害再算一次。
- 表现侧不运行真实 Weapon.step / Unit.die，避免生成第二套伤害、奖励和剧情；特殊武器保留实际轨迹有明确用途。
- 动作阶段与最终显示阶段都需要存在。原生动画会重建服装，原生重画会换图层，部分动画调用会同步重入事件；直接去掉最终纠正会恢复旧问题。
- 掉落的领取确认、地形的预测回执、共享暂停的双方原因，解决的冲突不同，不适合压成一种无条件覆盖。
- TcpLink 的有序分帧、BinaryMessageCodec 的纯数据约束、RoomCodec 的检查点压缩职责清楚。可以减少送入的数据，暂无证据要求重写传输层。

本体与代理的双对象设计受原生限制：Bullet.as:503/513 遍历 loc.units 并排除 disabled；Sats.as:453 遍历同一表，drawUnit 读取 vis。直接删代理、把代理伪装为 NPC，或将 vis 清空，会伤及原生命中/目标选择。应先明确适配契约，再尝试减少兼容代码。

## 建议的整理顺序

| 阶段 | 具体工作 | 完成时应能证明 |
|---|---|---|
| 1：先收口生命周期与重复发送 | 处理 B1；明确唯一周期快照发送点；帧内复用采样；退掉 S5 的旧业务路径 | 离线和独房无消费者时缓存有界；同源帧不重复构建；命中、拾取、换房前待结算请求不丢 |
| 2：统一播放和帧阶段 | 实现 B2 的同对象统一源时间；将已有前/后/最终显示调用顺序集中列出并执行 | 快速转身、短脉冲、成批收包、SATS 进出时，身体/枪口/弹道用匹配时刻；最终显示仍可恢复原生重画后的图层 |
| 3：集中状态归属与退出清理 | 房间上下文持有房间身份/角色；敌人记录持有本体/代理/显示；门箱、掉落和墙体按字段明确负责者 | 进入、退出、死亡、复活、换房、断开各有一个入口，不再向三个清理清单逐项补登记 |
| 4：最后收紧数据与历史适配 | 特效事件使用稳定流号、序号、增量轨迹和结束标记；从持久房间进度中排除已过期的短暂演出历史；迁出旧驱动，更新架构文档 | 保留在途效果和必要恢复能力，打包成本不随无用历史增长，发布构建只留下必要诊断 |

统一入口不意味着让所有消息共用一个“ready”布尔值：房间交接前的旧房回执、跨房共享暂停、当前房间抓取，允许条件本来不同，应由明确的消息类别表达。

已有测试用于保护行为；整理期间先跑相关边界与固定回放，最终候选继续走完整门禁。优先补的证据是离线/独房持续开火的缓存边界，以及敌人身体—武器—弹道源时刻的一致性。没有证据承诺整理后能提升多少 FPS，也没有建议扩大到公网、多人与版本兼容。

结构轴：6 项，最重要的是分散的时序与生命周期归属。行为轴：2 项，最高优先级是无发送消费者时弹道记录无法正常退役。下一步开发宜先收口这些基础路径，再继续叠加个别武器或敌人的补偿分支。
