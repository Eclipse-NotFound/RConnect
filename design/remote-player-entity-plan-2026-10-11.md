# 专用远端玩家实体：详细重构方案

日期：2026-10-11。状态：**设计提案，等待用户决定是否恢复实施。** 本轮只调查、规划和制作图解，没有改运行代码、编译、启动游戏测试或部署。

[先看图解](remote-player-entity-preview/index.html) · [此前评估](remote-player-entity-2026-10-11.md) · [原任务停点与遗留](../state/cooperative-hazards-2026-10-11.md)

后续讨论：第 1–13 节保留此前“统一远端呈现、保持既有执行归属”的方案。用户随后提出加入侧发送动作清单、由主侧真正执行的方向，新增在第 14 节；这是另一种更大范围的执行归属设计，尚未选定。现有 HTML 对应前一方案，不把新设想冒充已实现机制。

## 1. 用一句话说清楚

给每位队友在本机建立一个专门的“远端演员”：它能出现在世界里，也能被发现、瞄准和抓起；它的身体、装备和附着效果由同一个负责人管理，照着对方发来的、带时间的动作记录一起播放。

对方真正开了一枪，本机就重现**那一枪已经确定的结果**。不会让这个演员重新决定散布、重新扣弹药、重新结算一次伤害。

这仍然需要传递状态和事件。“实体”是每台电脑自己创建的游戏对象，不能把另一进程里的对象、函数和显示树直接搬过来。改善来自统一管理和正确重放，不来自给类换一个名称。

### 期望达到什么，不能据此保证什么

| 期望 | 实际改变 | 限制 |
|---|---|---|
| 枪跟着身体，弹从枪口出来 | 身体、枪的位置和开火使用同一份动作记录、同一显示时刻 | 源端漏采的一枪不能靠接收端凭空补出 |
| 换枪、护盾、念力不互相遗留 | 一个实体负责挂上、更新、解除和销毁 | 特殊武器、第三方模组仍需适配 |
| 加新效果时更容易完整支持 | 在统一入口登记来源、持续条件和结束方式 | 不等于所有未知武器自动兼容 |
| 减少卡顿与修复成本 | 消除重复驱动、重复对象和相互纠偏 | 网络等待、原版长帧、敌人负载仍可能卡顿；收益需实测 |

## 2. 对当前机制的修正认识

现在已经是 `RemoteDamageUnit extends UnitPonPon`，并已进入房间的对象和单位列表；它安装原生玩家外观，通过原生 `Weapon.create` 创建武器。发送的是位置、姿态、装备和效果数据，**不是逐帧截图**。[原生实体](../src/rconnect/game/RemoteDamageUnit.as:7)、[创建并入场](../src/rconnect/game/GameBridge.as:1399)、[采样](../src/rconnect/game/GameBridge.as:599)、[武器创建](../src/rconnect/game/GameBridge.as:1016)

已有成果要保留：玩家位置和武器变换已共享 `RemoteMotion.sourceTime`；`WeaponDisplay` 已保留枪械镜像翻转；念力、弹丸、门、遮罩、外观等已有专项处理。

仍有具体分散点：`WeaponDisplay.apply` 的枪械位置使用传入样本，但开火动画队列按本机 `now/next/cadence` 播放。原生 MovieClip 自己前进、装填起点和特效结束也需逐项归到明确时间。不能说“玩家所有部分都没有统一时间”，也不能因已有一个 `sourceTime` 就视为全部解决。[播放实现](../src/rconnect/game/WeaponDisplay.as:74)、[时间缓冲](../src/rconnect/game/RemoteMotion.as:82)

此前代码审查确认的敌人身体/武器混合时钟是**另一条路径**。本轮玩家实体重构可以提供以后共用的播放办法，但不把敌人重写暗中并入首期范围。

## 3. 基类选择：先用已工作的身体，再统一管理

| 选择 | 要付出的代价 | 本方案建议 |
|---|---|---|
| 完整 `UnitPlayer`，照常 attach/step/attack | 隔离背包、属性、输入、SATS、视角、宠物、全局 UI 和模组回调；还要防重复结算 | 不作首期路线 |
| 专用远端实体管理现有 `RemoteDamageUnit` | 明确原生可运行的步骤，集中拥有身体、装备、效果与时间 | **首期路线** |
| 完全自己画角色和武器 | 重做原生翻转、动画、混合与挂点规则 | 不采用 |

原版 `UnitPlayer.attach` 会把共享 `World.w.invent` 的 owner/gg、`World.w.pers.gg` 改成自己。创建第二名完整玩家会碰到“两个角色抢同一本背包”的问题。原生 `Weapon.shoot` 又包含随机散布和实际弹丸生成；不能把它当纯动画播放函数。[玩家 attach](../../../game-reference/decompiled/1.02/src102/scripts/fe/unit/UnitPlayer.as:401)、[开火](../../../game-reference/decompiled/1.02/src102/scripts/fe/weapon/Weapon.as:1421)

“一个专用实体”指**一个身份和一个管理入口**。内部允许有看不见的命中接收器。现有 `PeerHitUnit` 区分队友攻击，`RemoteDamageUnit` 接收其他原生命中；这些规则未被等价替代前不删除。`MirrorHitUnit` 属于敌人镜像，更不因玩家重构而顺手移除。

若隔离原型证明 `UnitPonPon` 的副作用无法控制，再比较更小的 `Unit` 基类与隔离后的 `UnitPlayer`。只有实证需要时才扩大范围；涉及游戏 SWF 修改另按既有权限处理。首期不要求复制完整背包或角色成长系统。

## 4. 模块分工：外面简单，里面把事情管全

以下名称是提案，不表示已经存在这些类。

```text
本机原版玩家 ──实际动作/结果──> LocalPlayerCapture
                                   │
                  已有 SnapshotPublisher / 编码 / TCP
                                   │
                                   ▼
                    RemotePlayerEntity（一个入口）
                    ├─ 身份、房间和生死代次
                    ├─ 动作缓冲 + 显示时钟
                    ├─ 原生身体 + 命中接收器
                    └─ 装备、姿态、护盾、附着光晕
                                   │ 发射已经发生的结果
                                   ▼
                  房间内的弹丸/光束/爆炸显示模块

实际受伤、掉落、房间账本：继续走现有结算模块
```

`RemotePlayerEntity` 的外部接口控制在四类操作：`receive(batch)` 接收已校验数据；`advance(frameContext)` 在规定阶段推进；`transition(change)` 处理房间/暂停/复活；`dispose(reason)` 一次清理。构造时注入原生对象工厂、房间上下文和现有结算出口。

接口约束也是设计的一部分：收包只入队，不直接改显示树；同一个阶段每帧最多推进一次；只有已获准的房间绑定能入场；销毁可重复调用但实际只清理一次；无有效身体时不能部分创建枪械。错误留下带身份的诊断，不用宽泛 catch 再偷偷走第二条世界修改路径。

内部可组合多个小模块，但外部不分别调用“摆身体、摆枪、换盾、清光晕”。否则只是把 `GameBridge` 拆成更多文件，协调负担仍留在外面。首期不引入通用事件总线、服务容器或全模组插件框架。

### 现有代码如何处置

| 现有位置 | 处置 |
|---|---|
| `GameBridge.spawnGhost/driveGhost` 及远端装备清理 | 迁入实体所有权；GameBridge 最后只交付房间与玩家批次 |
| `RemoteDamageUnit`、`PeerHitUnit` | 先原样保留战斗语义，交由实体创建/同步/销毁 |
| `RemoteMotion` | 保留已经验证的缓冲和插值；实体读取一次样本并共享；首期不改延迟策略 |
| `WeaponDisplay`、原生动画访问、外观/身体效果 | 成为实体内部绘制工具；去掉自身竞争的时钟和外部重复驱动 |
| `WeaponCapture` | 保留实际弹道采样，补足动作时刻与身份；不在接收端重算 attack |
| `ProjectileVisuals` | 继续持有离开枪口后的效果，按发射源时间域播放，独立结束和清理 |
| `SnapshotPublisher`、TCP/编码、`RoomSync` | 保留；只在明确字段契约处对接，不重写传输与房间权属 |
| 地形、容器、地图生成、掉落授予 | 独立于玩家实体，原有缺口仍单列处理 |

## 5. 传递什么：三种信息，各解决一个问题

### 5.1 连续状态——“这一刻站在哪、拿什么”

位置与速度、朝向、瞄准、站立/蹲伏/跳跃、身体姿态、装备、有效护盾与附着效果、抓取关系。状态带源时刻与动作阶段；姿态名和必要帧信息保留。对不能可靠从语义重建的原生剪辑，保留采到的帧/变换，不强求所有武器仅靠一个“正在射击”布尔值。

生命值、许可开关等逻辑事实及时交给原有处理器。画面可以稍微缓冲，不能顺便把伤害结算和禁止抓取也延迟到画面时刻。

### 5.2 一次性事件——“确实开了这一枪”

有效发射、开始/取消装填、抓住/放手/投掷、护盾启停、传送和死亡等。一次发射可有多颗弹丸；一个事件对应一组确定的弹丸身份，不把霰弹误当多次扣费。

发射记录带**实际枪口、实际方向/散布、发射时身体与武器姿态引用、弹丸身份和效果类型**。连续光束还需起止、变化的终点；追踪弹需真实轨迹变化；命中/爆炸由既有负责端给出结果。

事件不只从“两个快照的计数差”猜测。沿现有每帧采样/可靠原生回调收集，再批量随已有发送节奏交付；若一原生步内多次发射，需用实际弹丸/事件身份区分。挂钩的每个原生回调都要先审计副作用与调用顺序。

### 5.3 对照状态——“定期对一下有没有漏”

周期快照包含当前装备代次、当前有效动作/效果及最近事件水位。首次出现、换房、复活提供完整状态。持续护盾可由完整状态恢复；已结束的旧枪口火光不能在很久后全排队重播。

有效命中与物品结果不能当成“过期动画”随手丢弃。表现过期与业务确认分开处理；不宣称断线下的无限期、恰好一次保证。稳定重连仍在排除范围。

### 身份信封：每份动作单写清“是谁、哪一条命、哪间房”

建议字段（优先复用既有字段，只有缺失时才新增）：

```text
sessionId + playerId + incarnation        // 哪场联机、哪个人、第几次出生
roomKey + roomEpoch + roomTerm             // 前景/背景房身份、房间版本/授权期
sourceTick/sourceTime + sequence           // 源端哪一步、哪条记录
equipmentGeneration + actionId            // 哪次装备、哪次动作
projectileId / effectId / targetIdentity   // 哪个弹丸/效果/被抓对象
```

`roomTerm` 是房间负责人那次授权的标记，不与复活代次混用。装备代次能区分两次拿起同一把枪。目标引用必须包含目标的生死/房间代次，不能只用会复用的数组下标。

TCP 在同一连接中有序，但房间交接、缓存和销毁后重建仍可能让旧数据晚进入处理阶段。去重键防重复；代次防张冠李戴；两者用途不同。不为本次重构另造 UDP 或大规模可靠传输层。

双方使用同一候选并协商是否支持实体动作协议。迁移期旧数据转换只保留在一个入口；对能力不匹配明确拒绝该实验路径，不静默拼接半套新旧事件。这里不是扩展游戏版本兼容范围。

## 6. 一枪如何从本机到对侧

1. **本机真正开枪。** 原版决定散布、扣弹药并生成弹丸。采集这一真实结果，不能先猜一次再让原版开一次。
2. **一起发出动作单。** 身体/枪械在开枪时的姿态、装备代次、枪口、弹丸身份带同一源时刻；在已有发布批次中发送。
3. **对侧等到对应显示时刻。** 在同一帧摆好身体和枪，处理上下翻转，播放该次枪口动作，从记录的实际枪口创建显示弹丸。
4. **弹丸继续自己的旅程。** 后续真实轨迹、命中和结束归弹丸模块；角色这时换枪或离房，不应把该弹丸错误挂到新枪上。
5. **实际结果只结算一次。** 世界/角色既有负责端算伤害，回报实际结果；伤害数字复用这个结果，不由“看起来打中了”再算一遍。

需要同时检查三种坐标：世界位置、身体内挂点、相机显示位置。网络发送世界相关坐标，不把相机缩放/偏移烘进枪口。源端真实武器变换保留原生翻转；朝向跨临界角时镜像符号离散切换，避免把枪压成一条线。

迟到的短事件若还有完整帧历史，可播放可恢复的短效果；已经过期的效果按统一策略收敛，不无限延迟射击节奏。新鲜动作不能被几秒前的枪口火光堵住。具体窗口沿用已有有界历史后再用实测决定，不能为“流畅”无界补播。

## 7. 时间：每名演员只有一个画面进度

像播放一段带时间的动作记录：身体在第 10 步，枪和它身上的盾也在第 10 步。源端每次有效采样有时间；接收端沿用 `RemoteMotion` 把源端时间映射到本机，再平滑推进。

两台电脑的 `getTimer()` 起点不同，不能直接相减当延迟。每个源端有自己的时间域；“同一时刻”指同一演员及其动作所用的对应源时刻，不要求所有机器计时器数值相同。

| 阶段 | 做什么 | 不允许混在此处做什么 |
|---|---|---|
| 收包 | 检查身份、房间授权和数据，入有界队列 | 即刻跳转身体、播放一遍开火 |
| 原生逻辑步前 | 更新合法逻辑位置、命中接收器与许可 | 改本机输入/镜头归属、跑远端玩家自主 AI |
| 显示推进 | 取一次显示样本；按同一时刻处理身体、装备、动作和附着效果 | 各工具重新采时间、各自建 ENTER_FRAME |
| 绘制前收口 | 原生剪辑重建后重新绑定挂点、遮罩并校正一次 | 第二次开火、第二次推进动画或业务结算 |

逻辑位置与显示位置必须明确分开：逻辑用于敌人感知和命中，显示可能缓冲。首期保持既有命中规则，只统一显示所有权；不在一次重构中新增历史命中回溯。原生 `setVisPos`、`step` 若同时写两者，要在原型中证明阶段顺序成立；做不到就停止扩大迁移。

保留已有玩家缓冲/念力低延迟策略。初期不靠加大发包量或增加缓冲掩盖问题，也不引入无依据预测。只有同条件测出改进，再单独调整参数。

## 8. 暂停、换房、复活：收尾必须和创建一样明确

### 共享 SATS / 菜单暂停

现有“任一端请求全队暂停、全部退出才恢复”规则不变。需要一个暂停批次：各负责端记录最终有效的模拟步与状态，接收端把身体、武器、附着效果和相关弹丸收敛到这一批次对应的终点，再一起冻结。网络与聊天继续处理。

不同源时钟用各自终点标记，不广播一个数字就假定各方时间相同。最终姿态应用后，同步原生命中/SATS引用，再生成或更新选择高亮；不能留“身体停在旧处，高亮已在新处”两套可见形体。恢复从冻结进度继续，不重播暂停前缓存。

这是需验证的衔接设计。玩家实体改完**不能直接宣布敌人 SATS 分裂已修复**；敌人也要使用相同的暂停终点契约，具体绘制仍走其现有路径并独立回归。

### 同图分房、背景门与整图旅行

房间身份以现有 `roomKey/epoch/term` 为准，包含前景/背景房差异。先关闭旧房实体的接收资格，再清理绑定；新房授权与完整状态齐备后出现。跨房移动不能穿过墙壁插值。

只在本机当前可见房间实体化队友；异房保留轻量身份和状态，不把队友瞬移回来。跟随、剧情共同进入、宿主发起整图旅行沿用既有规则。原生镜头和 `World.w.gg` 一直指向本机玩家，远端演员入场不触发玩家 attach。

### 死亡、复活、断开

死亡结束活体接收与抓取，保留有界的死亡表现；复活使用新的出生代次。旧护盾、枪口事件、念力目标不能复活到新身体上。角色销毁不等于消灭已经飞出的有效弹丸，弹丸由其所在房间负责结束；换图/房间账本处理仍遵现有授权。

断开执行确定的清理，不新增稳定重连。全部监听器、显示对象、命中接收器、时间引用、遮罩与动画历史由所有者释放；保留计数检查，避免“角色没了，监听器还活着”。

## 9. 特殊武器和效果：逐类验收

| 类别 | 必须采到什么 | 对侧负责什么 | 代表检查 |
|---|---|---|---|
| 普通枪/连射/霰弹 | 实际枪口、每次发射、每颗弹丸身份、装填 | 翻转、后坐、枪口、轨迹、结束 | 轻机枪；左右/上下临界角；移动连射；一枪多弹 |
| 近战 | 原生挥动阶段、挂点/轨迹与命中结果 | 挥砍和命中视觉 | 左右换向、挥动中换武器，不重复伤害 |
| 投掷/酸性炸弹 | 放手时刻、投掷物轨迹、落点、爆炸/酸液持续期 | 飞行、爆炸、残留 | 角色换枪后旧投掷物仍正常；持续区只一份结算 |
| 光束/闪电/激光笔 | 开始/停止、真实端点、分段/闪烁、命中结果 | 连续几何与短光束完整帧 | 不延长短光束、不把闪电退化为直线子弹 |
| 火焰/追踪弹 | 原生轨迹/转向与效果年龄 | 维持速率和生命周期 | 稠密场景不积压成慢动作；源端长帧单独量测 |
| 魔法/护盾/隐身/燃烧 | 形态、颜色、透明度、阶段及结束条件 | 原生资源与组合顺序 | 护盾色形一致；隐身可见程度；无假翅膀 |
| 念力武器/物品/队友 | 施法者与目标身份、抓/放/投、实际运动 | 挂点、光晕、释放、移动 | 松手后能换目标；WASD与许可不变 |
| MSW 非致命效果 | MSW 实际作用与公开配置/事件 | 显示与原有业务出口 | 沿已认可规则短暂限制视野、保留操作 |

原版 `Weapon.animate` 有可复用的旋转/翻转规则，但传入的 owner/瞄准/姿态必须正确。只有审计后确认无业务副作用的部分才能在远端执行；不能把“叫 animate”当作天然安全证明。[原版动画](../../../game-reference/decompiled/1.02/src102/scripts/fe/weapon/Weapon.as:1966)

MSW 的逻辑常围绕 `World.w.gg`，且有独立加载域。远端实体不会自动运行其私有控制器。优先复用已有真实结果采样；确实需要新接口时再按授权与 MSW 协调。新效果要声明能支持的类别，未知类别保留已知可用路径并记录未覆盖，不能悄悄假装成普通枪。

## 11. 分阶段实施与停止条件

现在处于 **P0：规划完成、实施暂停**。以下各阶段仅为恢复后的顺序，无日历工期承诺；原生阶段顺序和特殊武器覆盖是主要不确定性。

| 阶段 | 交付与范围 | 进入下一阶段的证据 | 失败时怎么办 |
|---|---|---|---|
| P1 隔离身体 | 一名远端演员；建立/入场/清理；先沿用旧快照 | 本机背包/属性/输入/SATS/镜头引用不变；敌人能发现/命中；无额外角色 AI | 保留旧路径；检查基类副作用，不扩充武器 |
| P2 一支枪跑通 | 普通枪身体、翻转、装填、开火、弹丸走新入口 | 实际枪口对齐；事件一一对应；一次扣费/一次伤害；移动连射与共享暂停不倒退 | 在同一入口定位采样/播放问题，不给每把枪加外部兜底 |
| P3 不同生命周期 | 至少光束、酸性投掷、近战、念力、护盾各一例，再扩表 | 角色换装/离场不截断弹丸；结束无残留；暂停各类保持正确速率 | 不能用普通枪通过替代本阶段；回退该类别实验 |
| P4 房间与生死 | 同图分房、背景门、跟随、死亡复活、旧事件拒绝 | 不抢镜头；无复制敌人/旧效果复活；交接前后身份一致 | 保留失败场景与旧路径，不扩大正式使用 |
| P5 负载与长局 | 同条件旧/新对照、队列/对象/监听器观测 | 既有正确性门槛全保持；帧时/时差/内存无未解释回退 | 不靠放宽阈值过关；区分源端长帧、传输、显示等待 |
| P6 收口与候选 | 删除已替代的玩家显示入口/计时器；完整清单与正常加载 | 所有正式检查通过，精确字节审计，安装基线可恢复 | 未满足就保留候选，安装版不替换 |

实验采用**每名远端玩家只选一条生效路径**的开关。允许旁路只读计算并比较结果；不允许旧、新两个实体同时进入世界、同时命中或各播一遍声音/弹丸。切换优先在新会话/安全重新入场时执行，避免半枪切换。

迁移一类时让旧入口转换到统一契约；通过后删除被替代的调用者和状态。旧版本作为 Git/编译产物回退保留，不把所有历史实现永久挂在正式版本中。实验适配层有明确退出阶段，不留第三条同步路径。

### 最先做的可否证原型

在隔离游戏环境中只放本机玩家、一个远端身体、一支普通枪和一个敌人。依次转身、上下瞄准、跑跳、换弹、开火、被敌人打、离场重建。

如果**不执行完整 UnitPlayer.attach**仍能复用原生玩家外观/武器、不会改本机引用，而且原生命中继续有效，才值得进入复杂效果。当前代码证明已有部分基础；不能跳过对新的集中管理顺序的验证。

- 开发停点为 Git **0927470** / `probe-cooperative-56`，SHA `8f02fef5f34ff18943807381850ac982e762b13d4a2497eb536e926836a3a232`。已知拆雷、地图全图比较、压力/火焰等未过，不能称为完整绿基线。

### 验证分三层

1. **不启动游戏的固定回放：**喂真实采样记录，经同一实体接口验证时序、身份、换装、迟到/重复事件、暂停、清理；它不证明原生画面对齐或性能。

3. **最终候选回归和真人确认：**沿既有完整门禁与正常启动；由用户观察手感、连续开火、鼠标瞄准与低频背景门问题。自动图像/数字门槛不能覆盖所有观感。

## 14. 新讨论：加入侧发动作请求，主侧负责真正执行

状态：用户正在考虑，**未决定采用、未恢复实施**。本节记录 2026-10-11 后续源码核对与方案比较，不覆盖前面已明确保留的玩法范围。

### 14.1 与前一方案有什么区别

前一方案让远端演员照着“对方已经做完的动作”播放。本设想则让主侧收到“对方想做什么”，替加入侧的角色真正执行，再把结果送回。专用远端实体在主侧因此需要增加独立的模拟能力，不能只改动画管理入口。

```text
加入侧：按下开火，瞄准左上方
               │ 动作请求（不是自行认定的命中/伤害）
               ▼
主侧：检查装备、资源和状态 → 实际发射 → 推进弹道/碰撞 → 确认结果
               ├─ 主侧自己的屏幕显示
               └─ 发回动作/弹道/结果 → 加入侧在自己的屏幕显示

可选：加入侧按下时立即预演无业务副作用的举枪/后坐/枪口反馈，待确认后合并
```

“主侧负责动画渲染”应拆成两件事：主侧产生正确动作、发射与效果状态；两端分别用本地资源画自己的视角。无需让主侧生成加入侧的一整张屏幕，也不应让加入侧完整再开一次枪。

### 14.2 能带来的收益及剩下的工作

同一房间内，射击与敌人推进由同一端执行，可减少“加入侧认为打中，主侧认为没有”的独立计算分歧；散布、资源消费和实际命中有明确的唯一结果来源。对侧的枪口、弹道和特殊效果仍需以统一身份和时间重现，前一方案的显示实体仍然有用。

主侧原生执行成功，不保证加入侧自动显示所有效果。光束终点、酸液持续区域、念力关系、护盾形态和 MSW 自有控制器等仍需要被纳入结果采集/重放。漏采或错误播放时钟不会因为改变负责端而消失。

如果主侧只生成视觉弹丸，却仍让加入侧独立结算同一枪，这没有完成所提的执行统一。反过来，如果主侧把攻击也接管，本机原版攻击必须在产生弹药/伤害/掉落副作用前转为请求；不能两边各真正执行一次再试图消重。

### 14.3 动作清单是持续输入记录

- 移动方向、瞄准和按住开火是可更新的输入状态；持续射击频率由负责执行的一端按武器规则推进。
- 换弹、使用物品、抓取/放手、交互是有唯一编号的动作请求；不是预先安排几秒后的固定脚本。
- 每条记录携带玩家/出生代次、房间及授权期、装备代次、源输入序号和必要时间信息。主侧回报已处理序号，以及接受、拒绝或执行结果。
- 一次“按住射击”可以产生多次发射，每发有独立身份；一发又可能有多个霰弹颗粒。命令、发射和弹丸不能共用一个模糊计数。
- 换房、死亡、暂停与连接失效时清除或中止旧输入，防止旧“按住开火”在新房继续生效。TCP 有序不能替代实体代次和清理规则。

### 14.4 加入侧的即时反馈与校正

完全等待结果时，按下到看见动作会经历“请求过去 + 等待主侧处理 + 结果回来 + 显示缓冲”。这比仅显示别人已经发生的动作多了一次请求链路；没有本次实测，不能给固定毫秒数。

建议把两类反馈分开：举枪、视角、可安全隔离的后坐/声音/枪口反馈可先本地预演；伤害、正式弹药/魔力消费、掉落和任务结果等待唯一负责端确认。确认带原请求/发射身份，接收端把预演认领为正式动作，不再额外播放一次；拒绝则撤销可撤销部分，并更新资源/动作状态。

本地预演不能直接调用当前有真实开火副作用的完整 `attack`。普通枪的几何预测也不能自动推广到追踪弹、闪电、爆炸和其他模组；第一原型可只预演角色与枪口，再逐类决定是否需要视觉弹丸预测。

若连移动和碰撞也交给主侧，就还要记录未确认输入，根据主侧位置校正并重放本地输入，这比视觉预演复杂。若移动继续由加入侧决定，则应准确称为“主侧执行战斗”的混合方案，并为开枪位置采用哪份已接受状态定下规则，不能声称所有行为已经主侧权威。

命中按哪个时刻的世界计算也要明确：可先以主侧执行时的世界为原型基准；如果加入侧看到的是较早的敌人位置，就仍有感知偏差。回溯到过去位置判定属于后续独立能力，不能把它当成统一执行自带的效果。

### 14.5 原版适配的实际门槛

源码证据：`Weapon.shoot` 在玩家路径中将持有者强制转换为 `UnitPlayer` 来读取卡壳/技能等属性，并创建实际弹丸、生成随机散布；装填直接读写 `World.w.invent`。当前 `RemoteDamageUnit` 是 `UnitPonPon`，仅把 `player` 设为 true 并调用完整开火，可能遇到类型/全局数据问题。[开火](../../../game-reference/decompiled/1.02/src102/scripts/fe/weapon/Weapon.as:1421)、[资源访问](../../../game-reference/decompiled/1.02/src102/scripts/fe/weapon/Weapon.as:1714)

主侧需要一份独立的战斗上下文：装备及状态、弹药、魔力、技能/专长修正和相应人物属性。全主侧模拟还涉及护甲、受伤、状态与死亡。它们需按受控顺序更新和确认，不能直接借用宿主的背包或把 `World.w.gg` 长期换成加入侧角色。

这不等于新增“互相查看背包/交易”玩法，但确实新增了角色战斗资料复制和资源归属管理，超过前一呈现方案的范围。复用原生功能的前提是隔离它读写的对象；MSW 等围绕本机玩家运行的模组仍需单独接入。不能预先承诺仅在现有远端身体上多加一个方法就能完成。

### 14.6 分房行动是最大的架构分叉

原版 `World.step → Land.step` 推进当前 `loc.step()`，过渡时上一房间有限执行 `stepInvis()`；这不是任意两个普通房间的完整并行模拟。[Land.step](../../../game-reference/decompiled/1.02/src102/scripts/fe/loc/Land.as:1567)

RConnect 当前对异房明确授予加入侧该房间的执行权。现有 `inRoom` 只是暂换房间引用后执行受控函数，不能据此认定完整武器、脚本、音效、视野和全局玩家上下文都已隔离。[房间授权](../src/rconnect/core/RoomSync.as:333)、[受控房间调用](../src/rconnect/game/GameBridge.as:6003)

| 选择 | 同房 | 分房 | 代价与影响 |
|---|---|---|---|
| 始终由主侧执行 | 主侧运行两名角色及世界 | 主侧还运行加入侧所在的后台房间 | 执行归属统一；需后台房间调度、独立玩家上下文，主侧负载增加 |
| 由房间负责人执行 | 同房通常由主侧执行 | 加入侧执行自己获授权的房间 | 沿用分房能力；仍要维护房间交接，不能称为始终主侧执行 |

两条路线都可以使用专用远端显示实体。此前“普通房可分头行动”继续保留，不能为完成重构悄悄改回必须同房。离屏房间也可能需要推进原生动画/效果状态；少画一个屏幕不等于模拟成本消失。

### 14.7 建议的判断顺序

1. 先确认目标收益：若重点是统一战斗结果，主侧执行值得做原型；若只是枪口/动画错位，前一呈现收口改动更小。
2. 第一个隔离原型限同房、一支真实普通枪：加入侧请求，主侧实际发射；记录双方弹药/属性引用、实际命中、延迟与帧负载，证明只有一次执行。
3. 再加可撤销的本地视觉预演，覆盖主侧接受/拒绝、按住/松开、换弹、换枪、暂停与死亡，证明确认不会双播或继续旧动作。
4. 然后专门验证分房路线与特殊效果。若目标是始终主侧执行，后台房间模拟必须过关，不能将同房原型当作可替换现有完整合作功能的候选。

推荐作为候选方向继续比较，不在本轮选定全主侧或房间负责人方案。它与专用远端实体相辅相成，但把“播放者”升级为“执行者”是额外工作。本会话的实体实施仍暂停；地图支线另按用户恢复请求推进，二者不混用授权和验收。前一 HTML/静态检查对应当时的呈现提案，不作为本分支的实机或页面验证证据。
