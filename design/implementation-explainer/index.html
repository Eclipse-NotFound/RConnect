两边都有房间、人物和敌人。自己的键盘、鼠标先作用于本机角色。

以上是机制示意，不是游戏录像；H＝主侧玩家，J＝加入侧玩家，E7＝同一名敌人的示例编号。

“同步”就是持续交换并对齐状态。对方的画面由本机重建，因此位置、动作、开火和血量都要分别处理。

专业说明：这属于什么联机方式？

它是给原单机游戏增加的状态同步与事件同步方案：每端运行原版程序，交换玩家快照、房间快照、命中报告、交互请求及确认。“快照”是一份某时刻的状态资料，不是截图。它没有把整台游戏的画面当视频传输，也不要求两端仅凭相同按键就算出完全相同的世界。

当前传输使用 TCP（一条按顺序交付数据的连接）。TcpLink 用长度前缀拆分消息；握手协商二进制编码，未协商成功时保留 JSON 文本编码。TCP 的有序传输不保证及时呈现：发送方卡帧、积压和接收方绘制仍可导致延迟。

依据：S1 · 入口与通信 / 下文模块名称以已保存候选 f81c4d9 为准。

讲解基准：2026-10-10 已保存源码 f81c4d9；安装文件于 2026-10-11 只读核对。正在并行修改、尚未保存到此版本的代码不作为本页结论。

一“帧”就是游戏的一次更新。接入时机也属于实现的一部分：原版重画后，模组还要确认显示没有被覆盖。

专业说明：源代码、SWF、加载入口分别是什么？
.as 源码：人写的规则编译 →.swf：可加载产物加载 →init(main)：拿到游戏入口

Remains 运行在 AIR 环境中，游戏及模组使用 ActionScript 3。修改游戏 SWF 中的加载入口，使其加载 mods/Rconnect/release/RConnectMod.swf，再调用 RConnectMod.init(main)。这里的 main 是正在运行的原版主对象，接入层经它找到世界、房间和玩家；原版规则与资源可继续复用。

帧处理利用 ENTER_FRAME 的先后优先级及 RENDER 阶段。它们不能随意合成一个回调：原版动画会重建显示对象，视觉模组还可能改变可见区域的遮罩。显示阶段的修正有实际作用。

依据：S1 · RConnectModS2 · GameBridge 帧阶段

专业说明：怎样防止回房后敌人复活，或旧消息改错房间？

RoomSync 由主侧协调房间归属，保存各房间的检查点，即敌人、门箱、破坏和奖励等状态记录。进入、离开及归属转移时，先结清旧房间报告，再提交并恢复对应检查点。加入侧单独所在的普通房由加入侧运行原生模拟；双方汇合后共同房间归主侧。

加入侧停止镜像敌人的自主思考后，原版子弹会跳过被停用的本体。模组补一个同位置的受击代理，让子弹和 SATS 能认出目标；它自己不再跑一遍敌人 AI，也不再生成一份掉落。

蓝色虚线是说明用边界。代理借用本体的图像引用，不额外画一只敌人。

专业说明：为什么两种伤害方向使用不同的数据？

加入侧 → 同房敌人：MirrorHitUnit.damage 调用原生 Unit.damage，把算出的净生命损失和护甲／护盾变化写回镜像；接入层从基线提取差额上报。RoomSync.report 校验房间后，主侧 GameBridge.applyDamage 以原生 D_INSIDE（代码值 100）应用净生命损失，避免再次减伤。最终死亡和奖励在房间负责端发生。

敌人 → 远端玩家：负责模拟的那一端用远端玩家的原生化身参与索敌与碰撞。RemoteDamageUnit 记录命中输入，NativeHit 传递并恢复伤害类型、穿甲、暴击等必要字段，再在受害玩家所在端调用自己的原生 player.damage。自己的装备与角色规则由自己的端结算。

30 → 20 只是一次假设的结算结果。实际原版计算包括伤害类型、护甲、护盾、抗性与暴击等，并不是固定减 10。现有方案也不是所有伤害都由主侧重新验证的竞技反作弊架构；它有对加入侧报告的信任。

受击代理与本体共享图像，使原版 SATS 可以访问目标外观；也使遮罩、血条和清理更容易相互影响。这解释了为何“只删掉多余对象”可能重新引入打不中、双影或空引用问题。

依据：S4 · MirrorHitUnit / NativeHit / applyDamageS8 · 同步审查中的伤害归属

交换的资料代码中的目标间隔用途
玩家、搬运中物品约 50 毫秒较快更新位置与姿态
敌人、门箱、场景约 200 毫秒对齐房间状态

命中、拾取、换房等各自报告与确认流程及时结算一次性的变化

发送间隔 ≠ 游戏帧率。一个消息可以带多帧轨迹；忙碌时定时器也可能迟到。50 毫秒是默认约 20 次／秒的发送机会，不承诺每秒只画或一定画 20 帧。

只有一个“开火了”的信号还不够：曲线、翻转、命中和消失的时刻，都影响你看到的效果。

专业说明：状态、事件、确认各解决什么？

状态回答“现在是什么”：坐标、血量、门的开合；事件回答“发生过什么”：某一发子弹、某次命中；确认回答“这个请求是否已经生效”。这些语义有区别，但不表示每种都占一个独立网络包：轨迹与事件历史也会附在快照中。

候选中的 WeaponCapture 观察原生子弹和效果；UnitPresentation、ProjectileVisuals 在远端播放。接收端不再运行一次真正的开火、死亡或掉落脚本。原生特效可能持续多帧，即使换枪也要保留尚未结束的旧弹；结束记录要发送后再退役，防止最后一帧丢失或历史越积越多。

门的动作状态、墙的破坏、物品领取有各自的规则。比如门同时占用地图格子，单纯把格子状态覆盖回去可能触发错误的破坏动画；领取物品则需要唯一物品标识和确认，避免同一份掉落两边各捡一次。

依据：S5 · WeaponCapture / ProjectileVisualsS6 · SnapshotPublisher / ExplorationSyncS8 · 地形与对象归属审查

专业说明：真实代码怎样缓冲？为什么敌人多时仍会卡？

RemoteMotion 按源端 sampleTime 排列位置，估计时间偏移，用连续的显示指针取样。重复时间戳不会重启动画；指针不越过最后一个已收到的位置。玩家与高速搬运使用较高频轨迹，在适用路径上做保持端点范围的平滑插值；普通敌人使用较低频的位置流。上面的线性教学模型只展示共同原理，并非该算法的逐行移植。

真实缓冲深度会参考收到的时间间隔并设置上限；快速抓取、掉落弧线和普通单位有不同策略。暂时没有新位置时，它不猜测未收到的未来运动。settle 在暂停时把显示指针收至最新已收终点；传送等不连续移动另行处理。

密集战斗的成本至少经过：原版模拟 → 扫描采样 → 编码／收发 → 更新对象 → 绘制。任何一步吃满时间，都可能使记录稀疏或成批到达。只提高发送频率还会增加扫描和数据处理负担；缓冲也不能补回没有采到的真实动作。

已有审查发现敌人位置／弹道采用缓冲源时间，而部分姿态、开火动画从本机收包时刻开始推进。这是明确的结构问题，但不能据此把用户所有卡顿都归因于同一原因。当前密集开火和火焰时序测试仍未达标。

专业说明：哪些复杂度已收口，哪些还不能删？

本轮已提取周期发送器和源端武器采样器；damage / loot / objs / terrain 统一交给 RoomSync.report 接纳或拒绝；房间显示资源从统一入口清理。离线停止记录武器事件；有订阅者的结束记录须先发送，再保留短窗退役。加入侧独房保留活动弹道和最近结束记录，以供房间交接。

换房时的冻结、结清报告、归属标记和确认，有防止回滚及重复结算的作用；原生受击代理、显示遮罩恢复和最后绘制阶段也有兼容用途。优化要消除重复责任，不能只按代码长度删除保护步骤。

GameBridge 仍承担较多职责，敌人播放时钟和高速持物／常规场景字段归属仍有进一步整理空间。模块拆分不直接等于帧率提高；需要同条件下运行验证。

专业说明：怎样判断“没有损害实际运行效果”？

先冻结源码、实际编译产物、测试驱动、游戏与其他模组输入，再用隔离 AppID 和存档运行主侧、加入侧两份真实游戏。检查两端的日志、对象状态及需要验证的最终画面；不能只看编译成功或一侧没有报错。

既有记录保存了成功和失败。旧候选在当前环境也出现低帧，但顺序对照的装备与负载并非完全一致，而且新候选部分火焰时间偏差更大，所以不能说已经排除回退。未通过的门槛不能用其他通过项抵消。

本页仅核对既有代码和验证证据，没有重新执行游戏测试。显示演示使用合成数据；它用于解释机制，不用于证明候选性能。用户在真实游玩中报告的新场景，仍需单独复现。
