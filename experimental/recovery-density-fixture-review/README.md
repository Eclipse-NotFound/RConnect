## event-cost 的确定错误

driver03 `SustainedDensityTestDoc.as:188–189`：MESSAGE 高优先级监听只有 phase==load 才设 netAt；普通 message 监听在接到 density-commit 时执行 beginDensity（364），将 prepare 改为 load；低优先级监听因此开始累计，却读取尚未设置的 netAt=0。首个假样本是进程 getTimer 值 **72773ms**。

实测第一阶段 netMs=73859、netMax=72773；以后 netMax始终72773，netMs累计至81371。它不是一次真实72秒的网络处理，也不是某生产函数阻塞。第一阶段netMs及累计netMax不可用于网络成本归因。后续阶段netMs差分消去了这个常量，但仍仅是解码后 MESSAGE 事件派发部分，包含同事件中的测试监听，不是网络/反序列化完整CPU。

cpuMs/netMs/viewMs/motionMs 都是累计计数，不在每阶段重置；cpu测的是部分Stage ENTER监听跨度，view/motion还有重叠，不能相加或从整帧相减定位其它模组。cpu高优先级始终更新frameAt，没有上述 netAt=0 的相同错误。若后续另修诊断，应按同一个事件捕获“进入时是否处于load”标记，并只在匹配事件完成时计数；只重置netAt不能避免prepare→load跨状态误计。本审阅未修改统计或旧日志。

## 后续候选应如何比较

**严格比对的受控输入：** 同字节driver03、同游戏宿主/资源/其余模组与配置、相同角色身份和视口；按host对host、join对join比较原80个本体的种类/大小/初始位置/朝向/血量/禁用状态、武器种类和该角色执行参数；实际地形、碰撞/门墙状态、房间光照与颜色、相机；七阶段顺序、原时长判据和原断言。仍记录实际宿主发射量/帧数，因为 gun.attack 由宿主帧推进，FPS不同会反过来改变单位墙钟发射负载，不能只凭“12把枪”推断同吞吐。

**不能把真正时变观测当永久场景身份：** getTimer/UTC、nativeFrame、收包序号、弹体/Part的即时坐标/寿命、显示MovieClip.currentFrame和短暂alpha、冷却计时、即时瞄准角、插值中的对侧姿态、准备后对象链枚举顺序。这些应按类型/阶段保留为观测或负载协变量；做结构对齐时用稳定身份或多重集，不能因一个Part移动几像素就宣布整轮不可读，也不能静默删除其数量/寿命影响。当前准备摘要并未保存Part真实寿命，单张摘要不足以证明它立刻消失，因此不能量化扣除其成本。

**但本轮BackObj.frame/alpha不是上述动画时变字段。** 原生 `fe/graph/BackObj.as:96–177` 在构造时按资源/XML/随机数选frame，随后gotoAndStop；alpha来自资源/XML，onoff才改灯光frame。应继续视为真实绘制配置，不能为了比较方便统统去掉。类似静态Box多寡/位置也会改变场景工作。若下一轮同角色仍有这些差别，可报告固定80敌人负载下的现象和失败趋势，并列混杂项；不能据此给精确百分比或宣称严格同场景的整体性能提升。要获得严格归因，需要另行固定这些静态配置或在确有证据时限缩结论，不能追改本轮使其自动合格。

目前 audit 将整个 prepared JSON 逐字段严格比较，作为“完全同输入”的判据是保守且诚实的；但单一 input_comparable 布尔不区分核心受控负载、静态额外场景和时变观测。后续应分层报告这三类差别，保留原fail与原JSON，避免把有价值的七阶段证据和完整因果资格混为一谈。
