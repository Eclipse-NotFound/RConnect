# 近战高频历史缩减：证据与窄方案

数据来自候选03真实双人轮 `b49865e3c1` 的加入侧原始 wire 记录，具体路径、SHA及逐项结果保存在 `melee-suffix-equivalence.json`。没有运行新的AIR/JVM。

## 观察到的重复量

两把近战武器各433个高频包。armature发送10,455个帧实例，只有434个不同源时间；ripper为10,551/437。每包平均24.1–24.4帧，每把有121个完全重复源戳的高频包。这不是小规模的必要锚点，而是不断重发约800ms的完整历史。

两把近战的高频 melee 对象离线 JSON 字符量约5.97MB/15.23秒。实际线上使用二进制编码，不能把它直接称作网络字节或CPU时间；但序列化/解码对象数量会随近战敌人数线性增加，因此应该避免这些可预见的重复。前述单轮约0.5ms均值差不能证明由它造成。

## 最窄实现

只改一个高频调用点并新增 `MeleeVisuals.captureMotion(u,w,stamp,state)`；state采用当前 `hostShots[w]` 的独立武器流记录，原完整 `capture()` 和接收端均不改。

- 新流第一次发送完整历史。
- 源时间推进时，保留上次高频发送末点之前最近的一个锚点与全部新帧。
- 相同源戳再次发送，保持同一个窗口起点，但从最新 observed.frames 重新slice；不缓存payload，最终RENDER换过的末点仍会送出。
- 完整快照不推进高频窗口，也不裁剪完整历史。
- TCP按序交付；接收端每个 `[a,b]` 插值窗口使用 b.melee，后缀完整覆盖该区间。同戳包会替换last.snap，因此不能简单每次从最新motionAt重裁成单帧。
- 发送流重建时窗口随hostShots记录重建，不跨会话或不同authority沿用。没有添加确认消息、接收缓存或新的时间轴。

## 实际数据重放

按0.5ms步长，独立计算旧完整历史和新后缀在接收端每个实际 `[a,b]` 区间的武器姿态、轨迹、根帧、可见性、颜色及bodyAlpha。

| 情况 | 两种武器合计游标比较 | 不一致 |
|---|---:|---:|
| 原 full/fast 交替 | 110,742 | 0 |
| 原 fast 流（含相同源戳） | 95,490 | 0 |
| 保留真实帧、抽稀到约133ms发送，完整包继续交替 | 102,232 | 0 |
| 保留真实帧、抽稀到约250ms发送，完整包继续交替 | 111,082 | 0 |

总计419,546处相等。慢发送案例是原轨迹的离线抽样，不是新实机性能结果。原交替流每武器187个同戳包；实际同戳内容变化次数为0，因此没有把最终RENDER“同戳改内容”说成已实测覆盖。实现保持窗口起点但不缓存内容，静态核对其能够使用新末点，根会话可在后续实测继续观察。

原高频帧实例21,006降为2,182，约减少89.6%；离线JSON代理5.97MB降为0.652MB。源帧、插值结果、完整历史未删减；不等于已测得89.6%网络/CPU降低。

增量补丁为上一层的 `melee-suffix.patch`。根统一编译及实测后再判断本机部署资格；本目录没有启动游戏或写release。
