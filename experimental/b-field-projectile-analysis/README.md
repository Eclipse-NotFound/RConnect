# B 弹丸采集与呈现延迟调查

2026-10-25。精确基线：`build/ab/b190-field9-build/src`（已安装 B3-0.1-field3）。原生依据为 `build/ab/native-hooks-019/verified/scripts`，不使用 B195 未合格优化。

本目录是调查与低干扰诊断稿，不是优化候选。未运行 AIR、JVM、编译或部署；不修改冻结构建、安装版、共享记录。产品改动仍以根会话整合和实测为准。

## 可确定的结论

1. 一枚存活弹丸在正常世界帧内最多被 `RoomRuntime.projectile` 完整采集五次：玩家推进后、自身推进前、自身推进后、房间及武器/战术服务后、EXIT_FRAME。每次都会走 VisualPose，尽管其内部会复用内容相同的不可变结果。
2. 这五个观察点不是相同语义。出生事件保存首次观察到的快照；自身推进后保存终点；后续全房扫描用最后一次已有快照补齐“被其他对象移除”的终止事件；EXIT_FRAME保存原生时间线已完成构造的最终可见树。只按 tick 缓存，或把中间全部换成位置采样，会改变上述事件。
3. 加入侧的弹丸、房间地形和效果走同一个 `PlaybackClock`。该时钟的目标缓冲可从 65 ms 上升至 250 ms，确实会让已收到的火箭及破墙确认继续等待；但这不是全部延迟，也不是每包固定等待250 ms。
4. 当前安全且有源代码证据的直接优化仍是另目录 `b-field-sync-fixes` 的普通墙体局部更新。弹丸采集暂不删观察点，先分阶段计时确认成本。

## 为什么不能直接五次变一次

| 观察点 | 被依赖的行为 | 直接删除的风险 |
| --- | --- | --- |
| afterPlayers | 玩家刚制造的弹丸的首个状态 | 出生会变成已前进一格或更晚的状态 |
| beforeObject | 房间中此前对象/探测服务可能修改的状态；新生对象也可能首次在这里出现 | 以旧快照替代当前出生/失踪前状态 |
| afterObject | 原生碰撞、爆炸、渐隐后的精确状态 | 同帧出生并命中的快弹丸丢终点 |
| afterRoom | MSW、战术及其他对象移除后的补齐；后续服务前的状态 | 外部移除回退到更旧状态 |
| exitFrame | 时间线跳帧后子树已完成构造；发布的运动快照 | 丢失火焰、激光、爆炸等实际显示状态 |

具体原生约束：Location.step 在玩家回调之后仍会运行 `prob.step`，随后逐对象推进、协调器和房间服务。Bullet.step 可修改根位置/角度/透明度、子节点 laser.scaleX，并在其他路径 `gotoAndPlay(2)`。PhisBullet 还受抓取、探测和爆炸影响。任一外部动作可能移除或改变另一枚弹丸。即使对象没推进，不能据此断言其视觉树未变。

现有 `capture` 的缺失补齐依赖上一次 `latestByRoom` 的不可变记录。保留 DisplayObject 引用而延迟序列化不是保留历史：动画、滤镜、子树或像素已可能被改写。没有明确变更通知时，“同一帧”不足以当作视觉版本号。

## 可保持语义的分阶段重构

先分清三个职责，再决定能否移除扫描：

1. **生命周期记录**：稳定弹丸编号、首次可观察的出生记录、唯一终止记录。
2. **不可变视觉版本**：只有已证明所有写入都受控的弹丸，才可凭显式版本号复用；未受控对象保持现有完整采集路径。
3. **帧末运动状态**：EXIT_FRAME对活弹丸发布最终状态，禁止用前面尚未完成时间线构造的树替代。

需要补齐的原生观察接口是“构造/武器初始化全部完成”“显示被改变”“移除前”和“对象推进完成”。Location.addObj 本身不足以当出生完成：Bullet构造可能在这里挂链，而 PhisBullet 子类尾部和武器调用者尚未完成后续初始化。Location.remObj 在摘链之后调用 remVisual，移除前可保存显示，但不能不经验证就替代当前 afterObject 的终态；自定义子类可能在 remObj 返回后继续改变显示。

因此第一阶段建议只增加影子记录：旧链完整运行，新链不参与发布，逐弹丸比较出生、每个最终运动快照和终止事件。证据必须包含同帧生灭、爆炸移除其他弹丸、房间切换/清理、MSW特殊武器、抓回/丢出/爆炸、Sandevistan回放及时间线跳帧。只有某条可证明的路径完全等价，才让它退出旧路径；不允许把未知弹丸自动归到快速路径。

若短期没有原生写入通知，低风险范围是减少 VisualPose 中“先分配再发现完全没变”的临时数组/描述对象；仍逐字段读取并保留全部观察点。这可以减少垃圾回收，但不能声称减少了采集次数。该文件当前由UI子任务同时改动，应由根会话单独整合。

## 已准备的诊断覆盖层

`diagnostic-src/authority/RoomRuntime.as` 以及 `diagnostic.patch` 仅增加已有 Timing 计数，按阶段与武器分组：

- `projectile.pose.<phase>.<weaponId>`：完整视觉采集耗时与次数。
- `projectile.total.<phase>.<weaponId>`：整条弹丸快照耗时与次数。
- phase 为上表五个名字；视觉采集仍在原对象字面量中原来的求值位置。

开关继续用现有 `Timing.enabled`。关闭时不生成分组标签；启用时每组固定直方图约8 KB，五阶段×两类×若干武器，短程定向场景使用，不作为长期游玩遥测。计时粒度为毫秒，微小单次成本可能显示0，须看总量与总帧时间。标记开销也要用同驱动对照。该覆盖层没有添加 native 字段或抓取元数据，合并时不能覆盖根会话对 RoomRuntime 的独立修改。

建议根会话先测 missile launcher 与 balefire/野火核弹各自稳定存活阶段和命中阶段，再测密集混合场景。记录全五阶段调用量以及 host.publish、host.simulate、capture.pose、client.decode、client.sceneAndMap、client.present；不能仅因“5次”就宣布这是主要卡顿来源。

## PlaybackClock 的直接影响与可测指标

当前算法是 `wanted=clamp(p90(最近32个源帧间隔)+p90(到达抖动)+15,65,250)`，增加立即采用，下降每个有效确认包最多2 ms。`take` 不让呈现时间倒退，并逐个消费所有离散确认。delay突然增加时，目标时间会后退，但 position 不退，于是画面可能等待目标追上。这是缓冲扩大的直接停顿机制，不等同于弹丸物理停住。

房间、玩家房间代次、暂停及时间控制边界会清空统计历史并 flush；**不会重置delay**。所以新房间可以继承旧密集房间的250 ms缓冲，直到获得至少4个有效新间隔后缓慢下降。

纯算术复算（JavaScript复刻 pace 公式，2026-10-25执行；不是AIR实测）：40个240 ms间隔使delay达到250，之后持续33 ms无抖动，直到第28个新包才开始下降，第120个新包降到65，耗时3960 ms。若先触发清空历史的边界，则第4个新包开始下降，第96个新包到65，耗时3168 ms。此结果只证明公式的恢复行为，不能当作实机火箭延迟数值。

建议最小测量入口：

1. `ClientReplica.apply` 在 decoder.decode 后、clock.push 前记录本机 `getTimer()`，以解码后的frame对象作弱字典键。
2. 现有 `replica.confirmed(frame)` 在 render(state) 后调用；这里记录本机时间减第1步时间，得到**接收确认到完成显示**的实际等待。包含排队与渲染，且不受双进程计时零点不同影响。
3. 每次 present 记录 `lastFrame.time-clock.position`、`clock.delay`、queued、underflows增量与本次ready.length。前两者是不同概念：前者源时间差，后者缓冲目标。
4. 单个弹丸id的出生/终止，或指定墙tile的首次变化，分别关联“第一个包含它的解码帧”和“第一个完成它的确认帧”。先量化缓冲独占等待，再讨论缩短缓冲；不能用跨进程两个getTimer直接相减。

精确地说，在delay不变、未flush且没有后续卡顿时，某包解码后的有意等待约为 `max(0, delay-(arrivalTime-frame.time-offset))`。已经迟到的包可能不用额外等待；屏幕刷新和ready队列里的前序render还会增加实际完成时间。host frame.time通常早于整帧捕捉/编码完成，所以序列化耗时也会进入到达差，不能全归给网络或时钟。

## 低风险处理顺序

- 先验证局部破墙与实际捕捉/解码热点：减少卡顿后同一缓冲算法自然得到更小输入，所有事件、动画、频率和物理保持不变。
- 再根据本机接收到显示的量化结果，单独评估边界之后的缓冲恢复；仅清历史但继承delay确有源码证据，直接重置到65却可能在新房间同样慢时造成欠帧。需要快房→慢房、慢房→快房、SATS、时停及抖动注入对照。
- 若另做时钟候选，可评估按经过时间限定恢复速度，保留单调position、所有离散帧与相同插值规则；这是新时间策略，必须独立验证，不混入当前局部修复。
- 当前不建议按弹丸/墙独立提前播放：会使敌人、爆炸、伤害与墙体处在不同源时间，重新引入SATS分裂及穿墙等已知风险。
