## 已修改的重复工作

| 位置 | 原有路径 | 本次改动及保留边界 |
|---|---|---|
| `SceneSnapshot.capture` | 为每个目标在所属房间的单位数组中做一次查找，同房目标越多，重复比较接近平方增长 | 本次清理中按目标的实际房间建立一次成员表；保留其它房间的有效目标，不跨帧缓存成员 |
| `ClientReplica.render` | 每次确认和插值都扫描最近240 tick内的全部已消失子弹 | 原去重表配合按首次出现顺序的队列，只从队首移除过期项；240 tick、命中当帧显示、计数、暂停和退出规则保留 |
| `VisualPose.capture` | 先为所有子节点创建新数组和包装记录，再逐项比较，发现没变便丢弃 | 仍逐节点读取和递归；直接复用相同子记录，遇到首个变化才复制前缀，不修改旧确认 |
| `VisualPose.apply` | 原生预制节点也每层分配管理/清理字典 | 只为本模组实际补建的节点分配清理记录；所有原生子节点仍完整匹配和应用 |
| `FrameDelta.diff` | 每次递归都复制完整字段路径，即使该分支最后没有变化 | 本次编码使用一条局部路径栈，只有输出变更指令时复制路径；解码、协议、顺序和旧帧不可变规则不改 |
| `Link.drain` | 每个8ms接收批次后复制所有尚未处理的尾部数据 | 使用未读游标；大前缀且至少消费一半时才压缩，空缓冲清空；保留完整包顺序、半包等待、让出执行权和关闭收尾 |

这些修改减少的是已有工作中的扫描、分配和复制，不删同步内容或动画，不降低发送频率，不提前计算伤害。理论上有利于缓解主线程拥堵，但本轮没有执行证据，不能给出提速百分比。

接收缓冲的取舍：未读积压仍限2MiB、单包仍限1MiB；保留已读前缀后，正常接收路径的物理缓冲可能接近4MiB，压缩时短暂另有尾部副本。以少量额外内存换取减少重复搬运。原有CLOSE读取追加分支未加积压检查，本轮没有改动其行为。

## 时序审查后的保留项

- `Link.drain → WireCodec.decode → ClientReplica.apply → FrameDelta.decode → clock.push` 后才记录可播放时间。代码可证明本机解码耗时进入缓冲估计，但解码结束前帧也确实不可用；更早记时可能减少余量并重新欠帧。**未修改时间戳、65–250ms范围、缓冲回落速度或输入发送次序。** 上轮加速播放失败方案不回引。
- 输入发送在 `present()` 之后。它会读取确认后的对话、暂停、武器与SATS状态，不能只为早发送而直接交换顺序。
- `RoomRuntime` 对弹丸的前后步和阶段捕获有重复图像采样，但其中含出生、同帧命中、由其他对象移除、时停回放等生命周期观察。本轮没有删这些采样，以免漏掉短命弹丸或抓取目标。
- `NativeFields.apply` 不能仅凭“收到的记录相同”跳过：本机插值和原生显示会改目标字段。`FrameDelta` 的分支复制也保留，避免破坏播放队列中的旧确认。

## 静态审阅范围

主会话阅读所有差异，三个子代理交叉审阅，没有启动子代理测试。检查了子节点增减/过滤索引/隐藏恢复、补建节点的所有权、跨房目标、同tick重复渲染、暂停、队列过期、差异路径别名，以及网络半包/追加字节/回调关闭。静态未发现问题不等于运行通过。

`source-manifest.json` 固定基线和六个覆盖文件；`changes.patch` 是完整产品差异。`prepare.py` 仅组装新的源码目录，已保存但本轮未执行；它不包含编译、测试、启动或部署操作。后续需要时可组装至新的 `build/ab/b190-pipeline01-source`，再沿既有B构建流程生成候选，不能覆盖field5冻结构建。
