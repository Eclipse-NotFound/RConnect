## 已证实的串行依赖

准确 RoomSync `checkEarly → sendReady → commit → grant → restore → allowPaint → finishEarly` 存在以下顺序：

1. 主侧构造完成后发 seal，等待加入侧 ready，才在 `commit()` 内取得 checkpoint、打包并发送 grant。主侧自身绘制许可也在这条 handler 的末尾才放行。3876→4347 的 471 ms 是**构造完成到处理 ready 的组合等待**，不是 471 ms 的纯网络耗时。
2. 加入侧在 grant 处理里完成全量解码/恢复与入口放置后，才允许自身绘制。该 handler 实测 1843 ms；其中 restore 自身 1634 ms。加入侧不能把这 1634 ms 的状态恢复与“依赖已恢复世界”的绘制顺序颠倒。
3. 主侧完成自身绘制仍等待加入侧 ACK 才共同激活。因此“观察到主侧票据绘完”到“主侧激活”约 1980 ms 确实仍处于等待状态；其中包含加入侧后续工作、消息处理与调度，不是单一网络等待。

以上是当前代码/实测共同支持的依赖，不是建议删除这些步骤，也不证明任一步可以无成本提前执行。

## 已有实际计算耗时，不能相加错算

`RConnectRoomTiming` 字段是**从各方法开始累计**，`units/objects` 不是物体数量。

- 主侧 checkpoint 总计 **425 ms**：到 units 86、到 objects 115、到 terrain 424，即对应分段约 86/29/309/1 ms。主侧整个 ready handler 为749 ms，余下约324 ms 包含打包、角色/房间处理、发送等，现有数据不能再分开。
- 加入侧 restore 总计 **1634 ms**：role55、objects286、terrain817、units1536、effects1586、redraw1634；相邻差为55/231/531/719/50/48 ms。719 ms 区间包括移除旧单位、恢复/构造原生单位等该段操作，不能只叫“敌人动画耗时”。
- 加入侧 grant handler 比 restore 多 **209 ms**，包括解包、校验、入口放置等未单独计时部分。
- 425/1634 已分别包含在749/1843中，不能再加一遍；双侧工作有时间重叠，也不能把两端总和当玩家等待时间。

## 网络与绘制目前各缺什么

`A22 ROOM RECEIVE` 监听的是已解码 `TcpLink.MESSAGE` 的前后。TcpLink 在派发它之前已读 socket、重组包、解码；记录没有准确 socket 收包或发送开始/flush 完成时刻。prepare 的发送返回到对侧 handler 开始约3 ms，只能说明这一小消息当时没有大的后续间隔。ACK 日志到主侧 handler 约206 ms、主侧激活到加入侧 handler约147 ms，均包含事件队列/OS调度/解码等；**不能据此声称局域网络延迟为206或147 ms**。

Grafon 源码表明 `sceneEnsure()` 在 waiting 时返回；放行后走 `scenePreloadAll()` 或 `sceneEnsureUpcoming()`。实际像素生成还有 `scenePreloadRegions()` 的 region pass、`sceneDrawRegionChunk()`、位图复制与图层挂接。现有3.144/3.109秒长帧覆盖这些可能工作，但没有方法进入/退出时间，也可能含其它回调、资源分配或调度。**不能把两个长帧全额标为绘制时间。**

现有 `continuousSceneBeforeRaster` 事件在 `sceneOpen()` 中、准备阶段就触发，甚至发生在等待票据阻止真实绘制之前；它不能充当真正 draw-start。`sceneViewReady()` 只查询块存在性；ticket.unpainted=false 是完成状态，不含真实开始时刻。

## 与单人的对比限度

单人首段 ready=7179 ms、按键移动=7702 ms；双人主/加 ready 多3189/3359 ms，移动多3824/3800 ms。单人只有一次6517 ms原生构造长帧，没有分离构造和绘制的 marker，不能把它与双人某一个长帧直接作计算效率对照。

三者的种子与240×125尺寸相同，但**尚未验证完整输入场景等价**：单人最终入口为(161.8,4320)，双人约(1160,4800)；`loc.units.length`分别188/184/314。加入侧数组可能含同步代理，不能把314当真实敌人数；入口变化也不能单凭此证明地图布局变化。但它们足以说明“同种子同尺寸”不能替代地形、实体及入口工作量指纹。没有精确全场景指纹和重复配对，以上差值是本轮记录，不是优化收益、劣化比例或单人门槛资格。

## 最小下一步诊断建议（尚未实现）

先使用 early2 验证退出许可修正，不把当前卡死样本继续用于首进收益判断。如需要分解剩余耗时，只建一个**诊断专用宿主/模组副本**，正常运行代码不改流程：

1. 在 `sceneEnsure()` 等待检查之后、确实调用 preload/upcoming 的前后各记一个内存 marker。它测量真实绘图管线整体（包含分配/复制），名称明确为 ensure-work，不冒称单次 BitmapData.draw 的纯CPU时间。若需确认首个/末个像素生成窗口，只在 `sceneRegionDrawPass()` 和 `sceneDrawRegionChunk()` 聚合记录次数、首次进入、末次返回、累计时长；嵌套单独计深度，不重复求和，不逐块写日志。
2. 精确记录 `allowPaint()`、grant发送开始/返回、加入侧grant handler开始/恢复结束、ACK/activate发送及接收时刻。现有构造尾标记保留；每个marker同时记录本机getTimer与Date、事务ID、房间/renderer身份。消息发送返回到接收解码后仍只叫交付/调度间隔；不引入未经测量的“纯网络延迟”结论。
3. 每侧每次旅行最多32条元数据，内存缓冲，待绘制结束或失败后统一输出；不截图、不枚举大显示树、不做每帧日志。不修改 payload、票据、退出计数、等待期限或旧断言。双侧从各自真正draw区间计算交集，并显式区分paint与恢复时间。
4. 性能正式配对前，在同一原生阶段记录地形/实体/入口的简短指纹。首次调查可承认两份场景不同，不通过改随机规则凑出“相同输入”。诊断版本无FPS/发布资格，最终必须移除观察器并按相同准确组合复验。

这份建议只补证据缺口，没有新增生产微优化，也没有预估它能省下多少秒。
