# 普通房 case3：22 点颜色算术独立复核

准确输入：`build/m52/recovery22-ordinary-wall-native-01` / run `215270505b`；RC22 `746eef…3e93`，ACC 隔离宿主。原生 JSON uint 为真值，PNG 的表示兼容检查不用于放宽双方颜色比较。输入完整 SHA256 与逐点变色时刻见 `evidence.json`。

## 结论

这不是已证实的透明度舍入问题。1089 个期望变化点中，22 点在对侧**完全保留开火前背景色**，其余1067点准确一致，无额外变化。22点都在世界坐标 x=1118/1119、y=320..330，即格(27,8)，紧邻目标格(28,8)。每点 alpha 不变，但 RGB 通道差为22–130级；不是以前的1级舍入现象。

源的353次真实 RENDER 观察显示这22点均发生变化；对侧367次观察中22点始终等于 baseline，原生层和显示层最终相同失败。这里仅能证明**观察到的**所有帧未写入目标色，不能排除未采到的帧中曾写入又恢复。原始失败保持，不授功能或性能资格。

## 与读写算术的关系

- 精确 `NativeWallColor.setter` 的 alpha255 分支直接返回原 uint；本组10点 alpha255，无透明度换算。单次或反复原样 `setPixel32→getPixel32` 不能用预乘舍入解释这里的24–104级不透明色偏差。
- 另4点是非零 alpha 的纯黑（3个 alpha126、1个 alpha62）；其颜色通道0可精确表示，保留背景亮度也不符合单纯“黑色无法表示”。剩余8点是 alpha126 的非黑色。
- 当前表使用 `setVector/getVector` 构建每个alpha的反查表，再供实际 `setPixel32` 使用。缺少某通道的精确前像时，代码回退直接通道值。**本轮未导出 alpha126 的运行时表，故不声称那8点所有通道都已单独实测可逆。** 不过这些点也完整保留 baseline，且与可精确写出的14点呈连续两列缺失，现有证据不支持将它们独立归为不可表示色。
- 旧真实组件 `recovery-wall-color-roundtrip-01` 7/0，六个旧观察色的 setPixel/setVector/setPixels 直接结果一致，反查可精确恢复；`recovery-wall-color-component-02` 10/0，65536个**由setPixel产生的**颜色状态可反查恢复。它们不是对任意draw内部预乘状态的穷尽证明，不能用它们替本轮22点发出新绿灯。
- 普通房RC实际 `put:426–427`、`replay:554` 均先调用 setter 再 setPixel32，没有先调setter后又重复setter的代码；replay按保存的逻辑色写回。原生检查器 `NativeWallSurfaceProbe:31–48` 从唯一实际前景Bitmap复制原生crop，再用getVector读uint，显示层另行draw；两者最终失败一致。因此不是把PNG反预乘差异错当失败。

## 停点与边界

不新增BitmapData反例组件：不透明与纯黑14点已足以否定“整组仅由颜色不可表示/二次读写误差导致”，继续跑颜色微测试对定位当前缺失区域没有必要。队列、采集格过滤及毁墙不复活规则由墙面代理独立核查；本报告不以仅有cell元数据的wire冒充已读取实际发送颜色。
