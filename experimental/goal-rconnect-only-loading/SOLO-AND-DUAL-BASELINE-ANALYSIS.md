## 单人为什么仍需数秒

准确 A796 回读 `recovery-room-first-raster-current-source-02/source/scripts/fe/World.as:1116`：`exitLand(false)` 从 100 开始，每次原生 step 减一；20 显示加载，19 调用 `game.enterToCurLand()`，16 恢复控制并开始淡入，1 恢复 HUD。当前驱动 `beginMission`／`gotoLand` 沿该默认参数调用（准确 Game.as:431–466），没有改为快速旅行。

实际三程均逐帧到 20，之前约 2.67 秒；19 后至原驱动要求的 `t_exit=0` 约 0.61 秒。因此约 3.28 秒属于原生计数流程。观察到每个原生倒数值通常对应两次 RENDER，不是两次实际 GPU 绘制的证明。

首程长帧：ENTER 20→19 间隔 3669；最大 RENDER 间隔 3685（同值20的第二次RENDER比首次晚1ms，故上表边界差为3686）。原生 stdout 对应 `创建地图 3124 + 进入地图 531 = 3655`，与长调用区间接近。返回基地、重访的原生进入记录分别 387、485；RENDER 20→19 为 420、517。剩余几十毫秒包含帧边界/其他回调，不能在无函数计时下进一步归因。

单人全部 925 个观察中 `busy=false`、`entryPending=false`，旅行 `cover=0`、`paused=0`；没有房间交接等待证据。观察器总自身耗时 46、单次最大 2，不能解释首次数秒主线程停顿。

按相邻 RENDER 状态保持估算，三程真正原生 vwait 可见区间分别为 3765 / 500 / 598；黑幕可见分别为 2904 / 2903 / 2904。黑幕包括前部淡出与后部淡入，两者都不是网络等待；原始 observer.spans 含 boot/rest/finish，不能直接作为三程数值。

## 为什么双人总时间反而短

78C `RoomSync.before:137–145` 在离线时提前返回；仅连接后执行 `advanceSharedTravelFade:269–280`。该函数在黑幕已全黑后将倒数推进到21，在16后淡入结束后推进到2。它保留20/19/18/17/16/1关键阶段，但省去装饰性倒数。加入侧 `GameBridge.startSharedTravel:6215` 还明确使用 `gotoLand(target,null,true)`。

双人的短总耗时首先来自这条已有行为差异，**不能认定联机无同步成本**。例如同入口基地程：solo入口和双侧入口均 `(961.8,800)`、相同视口；原生进入耗时 solo387、host460、join377，RENDER加载段420/502/416。之后 host 仍有219、join459至完成；加入侧在原生退出结束后尚等约344（原结果 `exitEnd=590`、总934），包含等待宿主及实际授权处理。该轮 host ready handler 41、join grant handler 73，不能与其外层等待区间重复相加。

首次／重访入口不同：solo `(161.8,320)`，dual `(1161.8,800)`。即使 seed 与 room key 相同，原生抽签入口、镜头和单位构成仍不同，不做严格性能配对。双侧 loc.units 长度也包含代理/远端等对象，不能叫作活敌人数。

此前最接近的普通流程旧记录为 `goal-ordinary-loading-solo-01` 的10431/5551/6897，以及仅禁LAD/RV/CS的 `goal-ordinary-reduced-solo-02` 的8616/3968/4941。当前onlyRC这轮数值并没有比它们更长；这些旧组的启用模组、入口/人口或观察器也不同，仅可作历史方向，不能据此给候选提速资格。更早大场景回程低于3秒的记录不是这条原生完整倒数流程的等价基准。

证据：两输出 `result.json`、`observer/host|join/native-loading-observer.json`；各真实 run 下 `host|join.log`（TRAVEL/A22字段）、`host|join.stdout.log`（原生创建/进入计时）。后续 UI 候选应继续逐程比较入口/视口、20→19构造区间及19后授权/可操作阶段，不用覆盖层持续时间代替总等待。
