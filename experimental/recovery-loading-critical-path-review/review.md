# recovery13 大图加载：串行关键路径复核

2026-10-22。只读核查；未修改生产、驱动或历史结果，未启动 JVM/AIR。准确组合为 RC13 `1177eb1a…fddb1` 与宿主 FD92 `fd92fbd5…6734e`，沿已有正式回执；不是16/17的性能结论。

**可确认的主要问题是工作安排：宿主先完成原生加载和首屏，才开始交付完整房间状态；加入侧收到后再恢复并绘制首屏。提前启动加入侧生成已生效，但它省下的前段时间又转成等待。现有证据没有证明一个安全的 RC 单点改动就能把17.36秒降到单人的7.93秒。仅延后加入侧首绘没有解决这条串行依赖，应停止把它本身当作性能修正。**

## 1. 原始时间轴直接支持什么

原始证据为 [双人96b09cd943](../../build/m52/recovery-first-raster-scene-dual-01/result.json)、[单人f1e94fd2b0](../../build/m52/recovery-first-raster-scene-solo-01/result.json)，相同外部驱动 `413bcfdc…b2c`、同22项安装输入。功能分别主47/0、加36/0、单35/0；均不代表加载性能达标。

| 流程 | 单人标志就绪 / 真实按键响应 | 双人宿主 | 加入侧 |
|---|---:|---:|---:|
| 首进240×125马哈顿 | 7928 / 8448ms | 9699 / 10571ms | **17356 / 18190ms** |
| 基地48×25 | 1960 / 2140ms | 2606 / 2793ms | 2836 / 3369ms |
| 重访马哈顿 | 4032 / 4525ms | 5558 / 6320ms | **12868 / 13771ms** |

`elapsed` 从本侧收到旅行通知开始；真实响应从主侧发起的同机墙钟开始，含原三帧无漂移基线。加入侧收到通知分别晚14/331/5ms，不直接拿两个进程的 getTimer 相减。三段实际出生坐标逐值相同，大图 `(1161.8,4800)`、基地 `(961.8,800)`。

以下全是加入侧 getTimer，相邻阶段可相加，非估算的网络延迟：

|---|---|---|
| 开始→原生 exit=0 首次观察 | 28362→33557，5195ms | 52508→53481，973ms |

prepare 在加入侧开始后128/41ms到达，处理2/1ms，立即启动原生 `exit=21`。因此“加入侧根本没开始加载”不是本轮原因。

最有辨识力的是重访：宿主原生 exit20→19 帧为 **89205→92690=3485ms**，加入侧同段仅336ms；加入侧先不生成 chunks，随后却在 grant 后又等3333ms才观察到 painted。首进相应原生长帧宿主7357ms、加4384ms。差值不能全部叫纯绘图计时，但结合明确的 gate 条件，能确认宿主的原生首绘和加入侧的恢复后首绘被放在先后两段，而非同时进行。

注意：painted 是外部驱动首次观察，不是函数出口。加入侧 grant 后实际整帧空档为 **39864→45545=5681ms**、**59872→65208=5336ms**，跨过 painted 和后续处理。不能把整段5秒全部归给 Grafon，亦不能全部归给网络积压。

## 2. 精确源码中的串行条件与重复工作

源码统一取 `build/m52/recovery-13/src/`；宿主 Grafon 取 `build/m52/recovery-first-raster-host-03/import/fe/graph/Grafon.as`；World/Game 取准确E159的 `build/m52/recovery-native-travel-host-01/after/scripts/`（FD92只改Grafon）。

1. **把“原生过渡结束”当成“能交换状态”的门槛。** `RoomSync.check:208`、`begin:238`、`sendReady:711` 均拒绝 `game.isTransitioning()`；`GameBridge.isTransitioning:1292` 包含任何 `t_exit>0`。原生 `World.exitStep:1134` 在19时已调用 `Game.enterToCurLand`，16时关闭原生加载画面，之后还逐帧倒数到0。完整 seal/ready/grant 直到这之后才开始，状态恢复不能与这段原生加载尾部重叠。prepare 只交付种子/生成参数，不含完整房间状态。
2. **宿主完整采集又在 ready 返回后才做。** `RoomSync.commit:744` 对本次目的地 `mine==null` 调 `game.checkpoint()`，再编码、发grant。实测 ready→commit 整处理首进1003ms、重访915ms；其中完整 checkpoint 569/461ms（30000格）。这不是多个秒全在网络上传；“处理剩余434/454ms”也不能全算编码。已经存在的优化必须保留：共同目的地的 ready 不传 fresh/own；宿主 nativeFresh 不自我restore；不能再建议删这两个已不存在的重复快照。
3. **加入侧本地初始化后再完整导入。** 两侧原生地图生成分别运行，通常互相重叠，不应称成双方串行生成。真正串行的是加入侧生成本地对象后，`restoreCheckpoint:6231` 在 foreign 路径移除本地敌人、按宿主完整状态构造并恢复，再建立命中代理。首进/重访恢复总1705/1633ms，其中物件252/232、地形441/415、单位874/847ms。旧独立诊断136单位纯构造435–505ms，只解释这一段的一部分，无法解释后续5秒。私有AI/武器/脚本及模组构造副作用未被快照完全替代，不能直接复用同id近邻或跳构造。
4. **绘图初始化有重复，完整地形图不应说画了两遍。** 原生 `World.ativateLoc:1071` 调 drawLoc；恢复地形必设dirty，`tileRedrawIfDirty:3517→World.redrawLoc:1102` 再次 drawLoc。FD92 `sceneOpen:712` 两次都做 sceneClear、scenePrepare、光照/背景索引、drawAllObjs 等；gate只延后sceneEnsure/chunks。因此“初始化做两轮”成立，当前ON下“完整地形栅格做两轮”不成立。`rconnectRasterPending` 禁止 RoomTerrainView 复用是必要的空图保护，却也取消了重访时可能成立的旧图复用。
5. **宿主已运行，而加入侧还在恢复/首绘。** commit发grant后宿主release，不等ACK；TCP顺序保证grant在后续快照之前。宿主恢复周期采集、加入侧最终放行后恢复镜像和报告。`TcpLink.onData:161` 同步排空完整帧，存在积压后连续应用的成本来源，但准确13没有逐次drain完整计数，不能据旧09的610ms直接给本轮5秒分摊。忙碌时 `RoomSync.accepts→canSyncWorld` 还拒绝世界状态，故也不能假定每个等待期包都被应用。通用合包/丢旧包会涉及一次性命中、爆炸、出生、掉落、永久破坏和时钟，不是本轮最小方案。

raw `loc.units.length=316` 不能当作多构造136个敌人：136个镜像各有一个 `MirrorHitUnit`，该代理也在units数组，不在原生firstObj模拟链。这个结构以前已存在；本次没有完整对象身份采样可证明完全无重复，但总数不足以证明首绘新引入重复敌人。

## 4. 最小有意义的修正方向及停止边界

**推荐先审查一个只限共同整图旅行的“逻辑载入完成”交付点，让完整状态恢复和两侧首次栅格绘制在原生加载期间完成。不要继续只推迟加入侧绘制，也不要全局删除 isTransitioning。** 这是待验证的生命周期改动，当前没有净收益证明。

窄接点是 `World.exitStep` 的 `Game.enterToCurLand()` 返回后（或该Game方法所有原生工作结束后的既有travel bridge通知），此时 new Land、reactivate、玩家入房/出生选择、lightAll、GUI、地图触发状态都已完成；不能把 `new Land` 完成或 `Grafon.sceneOpen` 入口当作同一时刻。原生 `Land.enterLand:1199` 在 ativateLoc之后才setGGToSpawnPoint，提前在绘图入口抓坐标会重现两侧出生不一致。

要产生主要收益，至少还需满足两点，缺一就不应宣称解决目标：

- **首屏重叠而非只提前发送几百毫秒。** 当前宿主进入这个接点之前已完成它的首绘。若只把seal从exit0移到exit19，最多重叠原生尾部，无法消掉“宿主先画、加入后画”主体。需要共同旅行专用的宿主预绘延后：sceneOpen通用初始化照做，暂不生成chunks；完整逻辑就绪后先冻结并交付权威checkpoint，再让两侧对最终地形/固定入口绘制。离线、普通分房、不支持的宿主继续原路径，不改随机算法。
- **冻结逻辑不应冻结原生加载推进。** 现 `hold()` 直接设World.onPause；`World.step:1256` 因此连exitStep都停止。仅把现hold/commit提前会卡住加载或多出串行倒计时。要安全提前，需要很窄的“共同旅行已构造但尚未授权”条件，将原生exitStep/相机/必要GUI推进与战斗/掉落等世界模拟分开。不能只遮画面后让未确认世界继续受伤/掉落，也不能靠t_exit强置0或onPause绕过。该条件需要准确宿主边界修改和原生验证，**不是现成安全的RC-only小补丁**。

在此边界内仍沿原 RoomSync/SeedRasterEntry 的身份、epoch/barrier、固定入口与完整restore；旧房间最后报告先结算，已有无人房records/所有权交还照原序，旧Game/死亡/失败/断开回退旧路径。加入侧须完整导入后定位到seal冻结入口、原生相机首屏真实ready、原生过渡结束，才ACK/放行。不得以当时已移动的宿主坐标替代入口；不得跳过死敌/墙/门箱/掉落状态。跨房普通门不进入这条早期整图通路。

这一路的可证伪条件：同一现有大图驱动、同22项和输入，记录完整checkpoint在第一次宿主chunks前已确定、双方绘图时间重叠；同出生且原三帧/1000ms与实际按键判据全部保留。若源码不能在不扩大世界模拟分工的前提下建立上述窄条件，**停止该方案，明确目前没有安全的大收益小改动**，不要把提前pack、缩短遮罩或微秒级消重包装为单人耗时目标已经解决。

当前不建议再堆栅格缓存或通用包合并。首次tile(3,108).shelf真实不等，不能删比较；直接复用旧完整画面不安全。任务仍未达到单人对应耗时，安装版不应因本报告而更新。
