**时间字段来自高优先级 ENTER_FRAME 开始，不是最终 RENDER 时刻。** 坐标是在随后去重的最终 RENDER 读取；所有记录 `dt` 与相邻帧首 `t` 差完全一致。故表内只能称“游戏帧首间隔”，不能拿它计算准确显示时延。原重复计数仅比较 `peerY` 且 Y 在地面上方 20 px；允许横向仍在移动，跳跃顶点也可能重复，不把每次重复直接定义为同步故障。

## 共同边界

念力与 continuity 的 `t` 确实在最终 RENDER 读取，但都按游戏帧去重；不能凭相邻采样之间的空白证明期间绝无额外显示专用 RENDER。当前证据足够保留端到端观察缺口和业务未解决判断，不足以给网络、GC、某模组或操作系统定因。三套输入正确和原功能通过均保留；没有与 574D 同条件配对，不推断相对性能改善。后续若要关闭卡顿问题，必须覆盖实际运动期间的时间连续性，不能只检查两点是否相同或最终是否到达。

## 附：暂停边沿立即发送已有 worldstate 的只读判断

准确21的 `CoopPause.refresh:190–204` 在暂停状态变化后只发送 `coop-pause state/report`，没有主动发送停止时的敌人端点；`Session:1063,1204–1231` 的既有常规发送口才采集 `enemyMotion`。因此一次暂停边沿复用完整发送口，可明确移除“宿主确认暂停后，仍需等下一次常规 timer 才主动发端点”这个等待来源。它不能消除已经存在的整帧工作、请求送达、网络、加入侧显示／覆盖层重建，现有证据不能量化收益。

**60cc 的 159 ms 不能分账：** 默认驱动未导出 `pauseTiming`、敌人 motion 到达时刻或 `endpointReceived`。42895 ms 的 `paused=true` 可以由加入侧本地 SATS 直接触发（`CoopPause:178–190`），不是宿主确认标记。宿主日志有暂停→自定义 endpoint 的顺序，但没有时刻。自定义 endpoint 到达时 `initialGap=0` 只说明届时逻辑位置已对齐。故不能分别算请求往返、timer 等待、到包后绘制延迟，也不能称 159 ms 都可被一次 flush 消除。

最小复用的安全边界如下，尚未实现／验证：

- 仅宿主**未暂停→暂停**的边沿调用一次，先完成现有暂停状态广播，不在每个 `refresh` 或每帧重复发；不改常规发送频率和协议。后续精确调用链审查将方案收窄为只保留局部边沿判断，不新增发送忙标记：实际发送失败可同步进入原有 `onClientRemoved→broadcastWorldState`，但它并不经过新增入口，因此新增入口的布尔标记不能保护该旧路径。`_paused` 在补发前已设为 true，重复刷新不再产生新边沿；补发自身异常局部捕获。此处是最终候选顺序的说明，不改变上述实测结果，也不声称完整 Session 的异常重入已由组件验证。
- 完整保留 `server.bound`、`rooms.canSyncWorld && rooms.authority && !isTransitioning()`、`RoomSync.stamp` 的 settled room／epoch／term；加入端仍走 `sameHostRoom/accepts`。分房且宿主不是该房权威时，该口不会为另一房生产端点，不能绕过此限制承诺全房间收益。
- 不更改 `_sampleAt`。`GameBridge.readEnemyMotion:5512` 使用真实原帧时间；`Session:502–506` 不按重复 `tick` 丢弃 worldstate，`applyEnemyMotion:5529` 只拒更旧 sample，`RemoteMotion.pushTimed:149–150` 接受同 stamp 并替换末姿态。故无需发明新时间戳来强行让消息被接受，也不能把高优先级暂停回调时的旧帧编号改为“新模拟帧”。
- 该口不是无副作用的坐标读取：`UnitPresentation.captureEffects:259–280`、`EnergyImpactVisuals.deltaRecords:190–205` 推进效果 fast 游标，`readLootSync(true)` 更新飞行保留状态，发送成功路径的 `wallPaintUpdatesSent` 推进快速墙痕队列。必须复用完整采集→发送→现有记账路径，不能先捕获然后因条件变化丢包，或为探测再读一遍效果；保持累计快照修复。
