# early2 checkpoint / restore 独立只读开销审查

结论：**有可证明的重复查表，但没有证据把它选为主要提速方案。**目前唯一保留的待测假设是“同一次 checkpoint / restore 内使用短期身份索引”；不实施候选，不承诺收益。现有记录不能证明加入侧 719 ms 的主要成本来自身份查找，更不能证明消除它即可达到单人耗时。

范围：准确 early2 源 `experimental/recovery-early-exit-authorization/src`，编译源 `build/m52/recovery-early-exit-compile-01/src`，候选 D356。六个相关实现文件与早交付 early1 源逐字一致，故可用 `3b3c31c5f5` 的首进分段记录解释这些实现。`audit.py` 只核对源码/日志，输出 `evidence.json`；未运行游戏、编译、改源或安装文件。这不是性能试验或技能测试。

## 实际数据支持到哪里

- 主侧 capture：425 ms，其中单位段 86、物件段 29、地形段 309 ms。
- 加入侧 restore：1634 ms，分段 role 55、物件 231、地形 531、单位 719、effects 50、redraw 48 ms。首进确为 `foreign=true / authority=false / retained=false`。
- 加入侧 grant handler 1843 ms 包含上述 1634 ms，不能二次相加。它们是方法累计墙钟时间，不是各方法独占 CPU 时间。
- `RConnectRoomTiming.units/objects` 是累计毫秒，**不是实体数量**。现有首进日志没有 checkpoint 的 N/M、resolve 调用计数或其计时。主侧最终 `loc.units.length=184`、加入侧314不能替代捕获时数量；后者还含命中代理。`B395` 是身份序号，不是可靠的实时物件总数。

## 已确认的重复工作，以及不能删除的工作

`ObjectIdentity.as:70–100` 的每一次 `resolve()`，即使已通过键取得对象，仍先 `list.indexOf(found)` 验证当前房间成员，再检查 `used`；失败后遍历整表，按 id/类/距离匹配。距离严格小于当前最优值，等距时保留原数组中更靠前者。

`GameBridge` 的一次主路径包含以下重复查找：

| 完整完成的操作 | 显式调用次数 | 位置与条件 |
|---|---:|---|
| checkpoint | N + M | 6169、6176；先产生带键快照，再逐条查回对象取得完整原生状态 |
| 加入侧完整 restore：物件 | 2M + I ≤ 3M | `reconcileObjs` 3009；新造 Box 后3024再查一次；6253再查原生状态接收者 |
| 加入侧完整 restore：单位 | N_keep + N ≤ 2N | 6279；6306进入 `applyUnitsSync` 后5647再查一次 |

N/M 为此次快照条目数；N_keep 为排除 `isSceneHitClass` 后的单位条目数；I 为确实构造 Box 并走到第二次 resolve 的次数。**所以显式完整加入侧路径上界为 2N + 3M，不是某个已测绝对次数。**这不计其他同步处理，也不计同步回调重入。同一次调用中 `indexOf` 和备用扫描各至多看当时的 L 个元素，逻辑上界为2L；AIR原生 `indexOf` 的实际CPU成本不能用这些逻辑比较次数直接换算。

单位719 ms段还包含原单位 `remObj/indexOf/splice`、构造函数、`putLoc/addObj`、原生私有状态/武器恢复、姿态及炮塔显示恢复、清除多余单位。`applyUnitsSync` 在 **effects** 段，不在719 ms段。不能把两次 resolve 或整个719 ms统一称为“重复动画”。

没有发现足以安全删除以下工作的证据：

- **原生单位重建**：`foreign=true` 时先移除本地敌人，再构造宿主快照单位。构造参数包含难度、类型、XML、炮塔隐藏类型；原生内部状态和武器随后再恢复。两侧相同种子不证明这些对象的私有状态、构造副作用或其它模组挂接相同。直接复用会触及已出现过的炮塔、地雷、武器与死亡问题。
- **完整恢复后的 applyUnitsSync**：除再次设置位置/血量，它建立伤害基线、冻结AI、机械可见性、念力保护、武器视觉与 MirrorHitUnit；不能把整次调用删除。正常存活单位的姿态在此处进入后续运动显示路径，和前面的原生恢复职责不同。
- **地形的多次遍历**：`TerrainSync.restoreCheckpoint` 先初始化恢复前 `base/observed`；原生表再全量校验，最后写入并生成恢复后 `observed`。`base` 仍代表恢复前基准，后续 `hostPatch` 用它检测差异，不能直接用恢复后状态代替。全量校验保留“坏输入不先改一半房间”的约束。现有计时没有分开这些遍历；不能把531 ms视作多余。
- **redraw 标记**：表恢复总是 `dirty=true`；已经绘好的房间有 `RoomTerrainView.unchanged()` 保留像素路径。首进待绘时该路径明确禁用。准确宿主的 `Grafon.drawLoc→sceneOpen→sceneEnsure` 会受 waiting 票据阻止真实绘制，因此第二次 sceneOpen 不等于又画了一遍完整大图。现有48 ms及票据记录没有证明此处存在可删的重复全图绘制。

## 唯一待测假设：事务内身份索引

候选含义仅为：在当前一次捕获/恢复期间维护“哪些对象仍在当前数组”和可能的候选分组，替代重复全表搜索。仍执行原本所有状态捕获、构造、恢复、碰撞与显示操作。不跨帧/跨房复用，不更改频率，不以种子推断相同。

它目前**未满足等价前提**：

1. `reconcileObjs` 会 `push` 新 Box，调用 `die(-1)`、交互方法和原生构造；外部模组可能同步回调。单位段会 `remObj/splice/push`，之后建立 MirrorHitUnit 还会改变同一数组。只在入口建一次只读索引会过时。
2. AS3 数组可以原地改元素而长度不变，或被替换为另一个等长数组。只验证 `length` 不能保证成员/顺序没变；单线程也不排除同步回调重入。即使只改 `id` 或位置，候选分组/距离也可能变化。
3. `enter/clearRoom/bind` 会改变身份归属；`used` 每个阶段独立。已绑定对象优先不依赖 id/类，备用路径却必须排除已绑定对象；空键、失效键、重复引用、重入和同距顺序都需保持。
4. 备用路径的 `probe` 对缺失/抛异常成员有既有行为，分组时提早读字段会改变读取顺序或副作用。若只支持已证实的原生静态对象，未知形态必须走原分支。
5. 索引自身构建、维护及失效检测有成本。若为了正确性每次仍整表校验，就可能没有收益。不能据 `indexOf` 的存在直接选中。

因此本审查只登记假设，**不提出完整实现或“收益已确定”的主候选**。

## 最小验证建议（尚未实施）

先在一个独立诊断副本中，以一次 `checkpoint/restore` 为范围聚合，不逐实体写日志：

1. 记录实际 N/M、初始/最大数组长度、resolve总次数、已绑定命中次数、实际走过备用循环的元素数、构造/移除次数。`indexOf` 复用原调用返回值计算逻辑搜索距离，不额外调用一次；它不是CPU指令数。记录同一次操作是否重入、数组是否替换及已知增删。
2. 在已有单位段内分别聚合移除、原生构造、`restoreUnit`、姿态处理与 resolve 墙钟耗时；物件段同理。resolve 前后时钟只用于本次诊断，不逐迭代取时间。毫秒时钟会将许多短调用记零；和嵌套回调/调度一样，必须作为测量局限说明，不能以零证明没有成本。
3. 每次捕获/恢复只输出一条汇总，按3段加载两侧各至多一条/操作，字段数和总条数固定。已完成的旧结果保持原样；诊断有额外开销，不授予性能资格。先看身份查找实际占比，若小于噪声或被构造/地形支配，停止索引方向。
4. 若确有足够占比，再在隔离组件逐调用对照旧/新结果：同id同距、失效键、已用对象、原地/替换数组、插删/重复引用、可变字段、构造回调、代理加入、重入与旧房身份。必须比较选中的对象身份及最终状态，不只比较耗时。
5. 只有正确性和组件成本都支持才建游戏候选；最终无诊断组合重新做同场景完整输入指纹、真实按键恢复与重复配对。局部查找提速不自动兑换整机加载通过。

本轮源级审查的停点是：**重复遍历存在；实际占比未知，尚不能选优化算法。**
