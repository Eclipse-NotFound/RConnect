## 生产恢复规则

此前恢复要求 ColorTransform 全部 8 个通道仍等于光晕值。原生 `UnitPlayer.setFilters` 会通过 `vis.alpha` 独立写透明度；它与 `alphaMultiplier` 是同一属性。这可能使颜色覆盖仍存在，却因为一个透明度变化而跳过整个颜色恢复。

现在按两组独立判断：

- RGB 组：3 个颜色乘数和 3 个颜色偏移，全部仍等于本光晕最后写入的值，才恢复这一组的抓前值。
- 透明度组：alpha 乘数与偏移，二者仍等于光晕值，才恢复这一组的抓前值。

任一组被新的本地效果改动，就完整保留那一组。不是逐通道混合颜色，也不把旧整份变换盖到新效果上。滤镜原有所有权规则不变；运动、抓取许可、网络、伤害和持续持有时的绘制路径不变。这段只在释放、重置或显示对象替换时运行。

## 原生测试：基线握手

原始驱动来自准确 `build/m52/recovery-drivers-02/tests/PeerGripTestDoc.as`，SHA256 `9a02ef6f083e9e3fec3a8cbf31f282dcb9050a799a331370e11df86b28561224`。保留 ROOT 加入的 Q 前同一能力夹具及其断言，没有恢复到旧的仅 ENTER_FRAME 设置，也没有添加抓取失败后的重试。

旧版双方各自等 1600 ms 再采抓前 RGB；宿主可能已 Q，加入侧随后把已抓颜色误记为“抓前”。新流程如下：

1. 双方完成原来的稳定条件后，在各自最终 `RENDER` 采基线；此时必须没有本机抓取、没有被队友抓取、levit 不是 2。
2. 双方通过 `baseline-ready` 交换已完成的基线记录。
3. 宿主看到两份记录才发 `baseline-go`，双方检查握手和显示对象身份，再进入原有 Q/holding 流程。

同一 TCP 流中 baseline-go 先于后续原生抓取包，加入侧不会在收到抓取后才补采基线。Q 仍只有一个原生调用点，权限检查、成功判据、原生抬升和光晕像素门槛不变。释放后仍严格要求本机 RGB 等于握手前基线；没有改成近似值或“只要没绿圈就通过”。

`PEER GRIP COLOR STATE` 在抓前最终 RENDER、Q 前、持有最终 RENDER 和释放严格断言前输出 RGB/alpha/滤镜、vis 身份、实际玩家和房间 cTransform、现存效果、位置和持有身份。各进程自己的 visId 只能在该进程内比较。诊断可区分抓前基线污染、正常场景/状态效果变色、显示对象更换和光晕恢复失效。
