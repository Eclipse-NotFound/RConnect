## 代码依据和无法反推的部分

`RemoteMotion.pushTimed` 原来每次把 `previousOffset-offset` 加到cursor。候选仍减小offset，但只有**单次**改善超过 `max(100,interval*2)` 才前移cursor；若几十次改善都小于100ms，累计校准会全部交给最多1.1倍的播放速度补偿。累积1600ms理论上可能要约16秒额外追赶。

这与本次逐步追旧跳轨迹相符，但实机测量没有启动前的队列、offset、cursor或真实sample调用参数。现有候选窗口内只记录到19+17+1+2+4+4+1=48ms的新最小offset改善；不能伪称看到了全部约秒级债务来源。另一个候选改动是固定插值切线；它能改变区间内速度形状，不能单靠现有记录证明对全部延迟没有作用。

`GameBridge` 在接包时调用push(getTimer())，随后sample(presentationTime())，常规显示又sample(presentationTime())；presentationTime取当前模拟帧的_sampleAt。新设计必须覆盖接包与显示使用不同时间点、以及同一playAt多次调用，而不只是假定每包立即对应一次显示。

## 现有37项为什么漏掉

- `MotionContinuityChecks.calibration`：普通/抓取各只有一次25ms改善，只检查同一个1655ms时刻不移动，随后没有恢复速度检查。
- `HeldMotionBufferRegression`：200ms缺帧后恢复规则发送，offset固定；不是连续微校准。
- `MotionCadenceRegression.enemyRecovery`：敌人的300ms传输停顿，使用不同的最高1.5倍恢复分支。
- `NativeEffectRateRegression`：有限特效期间的时钟和暂停边界，没有累计校准。
- `DropMotionBurstRegression`：有真实批次记录，但属于immediateStart掉落路径，不能替代普通玩家启动测试。

## 最小修正方向（设计，尚未实现）

1. push只更新可靠时钟估计，并保存待处理的正向校准量；不要在push中改变已显示cursor。重复/倒序包不累计债务。
2. sample只有在真实显示时钟前进时才处理一次校准；同playAt再次采样必须完全稳定。把校准债务和普通网络缓冲追赶分开，不能再丢弃所有小校准，靠1.1倍慢追秒级旧轨迹。
3. 下一显示帧一次性消化大量债务也可能造成跳变，不能直接宣称解决：需要联合检验恢复期限、跨帧位移/速度及接收端点边界。优先保持原正常场景的恢复范围，只把“何时应用校准”移出push；如果必须区分启动校准与已播放动画，先在固定输入上证明该判定，不凭600px阈值掩盖问题。
4. 有限特效retainRate的原时长继续保留；期间延后的债务不能丢，释放后验证恢复。settle/重置/传送必须清理过时债务；immediateStart掉落保留已有弧线用例。

以上仍有“大债务下一帧消化会不会跳”的未验证点，不是可发布补丁。

## 固定回放输入

`analyze.py --write` 在本目录生成证据和输入。`replay-inputs.json` 明确分开两类：

- 本次两轮真实加入侧测量窗口的到达/显示记录：保留原时间，不伪造测量前缀。它缺少初始队列，不能当成完整准确时钟回放。
- 构造的32次50ms改善（累计1600ms）及随后规则流：每次都低于100ms，源/到达间隔均不触发1000ms重置，坐标不传送。以后由原组件运行器调用**真实AS3类**，同时核同playAt不动、下一帧不重复消费、恢复时长、界内和有限特效；不能用Python模型结果冒充AS3通过。

当前只运行离线取证脚本，没有JVM/AIR，也没有修改原37项或运行门槛。
