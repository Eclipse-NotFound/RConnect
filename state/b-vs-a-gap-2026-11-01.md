# A 版对照下的 B 版性能不足审计

日期：2026-11-01。范围：只读检查 A 源码与 B 当前源码/运行证据；**未修改 A 源码、未修改 A release**。B 当前安装体为 J12（`7c2cc412…47a`），A release 为 `69060487…`。

## 0. 一句话结论

A 的体感优势不太可能来自单一“秘密优化”；A 源码里真正值得 B 补的主要是 **同房间地形保留、死亡/尸体跳过、UI 文字/字体缓存、整单位/ blit 去重**。B 在 **FrameDelta、姿态记录、播放时钟、显示房过滤、伤害数字模板** 上已经比 A 更完整，不能整体照搬 A；B 的宿主权威架构本身也比 A 的 peer-state 同步更重。因此应做“点状补 A 的长处”，而不是换回 A 的同步模型。

## 1. 版本与证据边界

- A：`build/github-a-release/src`，公开版 0.2.24-tcp1；A release SWF `69060487…`。
- B：当前安装 J12 `7c2cc412…`，源码 `build/ab/b-j12-source-01`；同字节功能/ABAB 证据在 `build/ab/b-j12-test-*`、`b-j12-clean-*`、`b-j12-total-01`。
- 没有做 A/B 同场景同环境的新 ABAB；下面的“A 有、B 没有”是**源码机制对照**，不是新的 A/B FPS 实测。A 的历史证据多为计数/生命周期/组件级，不能直接换算成 B 的帧时间。

## 2. B 相对 A 的具体不足（按优先级）

### 2.1 同房间地形保留缺失（最高）

- A：`RoomTerrainView.as:8-98` 在同步检查点恢复前保存 `style/backobjs/tileInputs/contours`，`unchanged(loc)` 命中时 `refresh()` 只恢复原生轮廓、光照、`drawAllObjs`、相机/HUD，**跳过 `drawLoc` 全房重绘**；`GameBridge.as:6272-6277,6344-6347` 在恢复/重访路径使用 `terrainView`，并记录 `terrainReused`。
- A 证据：`state/room-loading-2026-10-19.md:15-17` 实测 `terrainReused`；`journal.md:159` 一次恢复/重访对照 **48ms（复用）vs 383ms（完整重绘）**；`nativeui2-loading-review-2026-10-25.md:56-76` 有同类命中/回退对比。属**场景级实测**，不是整场 FPS。
- B：`ReplicaScene.as:78-95` 在 `key` 变化时直接 `dispose()` 并 `new Location(...)`；随后几何条件命中就 `w.grafon.drawLoc(room)`（同文件 `geometry` 分支）。B 虽有 `TerrainPatch`/增量墙体修补和 `capture.tiles` 差分，但没有 A 的“同一 Location 恢复时保留已绘制栅格”路径；`build/ab/b-j12-source-01` 内未找到 `RoomTerrainView`/`terrainReused` 等价实现。
- 影响：房间重访、检查点恢复、战斗后回房的首帧/恢复帧；A 的 48ms vs 383ms 说明这里可能有数百毫秒级峰值，属于 B 最值得补的结构性差距。
- 风险：B 的 `Location` 生命周期、`TerrainPatch`、`TerrainInk`、SATS/暂停栅格都不同于 A；不能直接移植 A 的 `RoomTerrainView`，需要 B 专用的“保留 Location/栅格 + 字段比较 + 回退”设计。

### 2.2 死亡/尸体每 tick 完整采集（高）

- A：`GameBridge.as:5525-5548` `_fastDeaths` 按 `sost:animState` 缓存；`sost>=3` 且死亡键未变、且该单位武器没有 pending flight 事件时直接 `continue`，不采集其姿态/武器/身体效果；有飞行事件时仍采集。A 报告明确把“大量敌人/尸体”列为未完成场景，所以这只是一层防护，不是 FPS 结论。
- B：`SceneSnapshot.as:86-102` 对所有非玩家 `room.units` 每 tick 采集 `NativeFields`、`VisualPose`、`HealthBarPose`、`AuthorityAnimation`、武器/血条；**没有死亡键缓存**。`RoomRuntime.capture` 每 tick 还会走对象链（`RoomRuntime.as:194-210`）。
- 影响：真实战斗尸体堆积后，B 的 host publish/capture 仍按尸体数线性增长；A 的死亡跳过能减少这部分恒定成本。B 此前 J15 的简单“冻结记录”尝试在 enemies join 造成 13 项视觉断言失败，说明不能直接冻结记录；应按 A 的 **`sost:animState` + pending weapon events** 条件只跳过“稳定尸体”的完整采集，并保留首次死亡态/爆炸/结束事件。
- 风险：死亡动画、血条、武器事件、时停/SATS；需用 enemies 的死亡阶段和真实战斗回归。

### 2.3 UI 文字/字体每 100ms 全量重写（中低，低风险）

- A：`RCLocale.as:74-93` `fit()` 以 `text+width/height` 为签名，未变直接返回，不再做字号测量/`setTextFormat`；`NativeTextVisuals.as:156-177` 伤害数字只在文本/帧/颜色/缩放签名变化时发送，接收端不遍历历史。
- B：`NetHud.refresh()`（`authority/ui/NetHud.as:265-371`）每次刷新大量 `.text=`，包括状态、按钮、页签、提示、聊天、设置等；B 的 `RCLocale` 虽存在，但 B 源码中未找到 `RCLocale.fit` 调用；每次 `refresh` 还会读 `textHeight` 做布局。
- 影响：UI 刷新约 10Hz，单次成本不大，但会造成周期性文本布局/字符串分配/GC，在 host publish 高峰时放大卡顿；A 的行为更稳。属**小改动、低风险**，可先做“值变化才赋值 + fit 签名缓存”，不碰 UI 布局语义。
- 风险：需要保证聊天/状态/错误文本变化仍即时；不能把固定标签的换行/字号锁死。

### 2.4 整单位视觉 apply / blit 去重不完整（中）

- A：`GameBridge.as:6446-6449` 同一 `selected` 视觉对象只 `_presentation.apply` 一次；`RConnectAnimationAccess.as:89-93` 用 `{id,frame,data}` 的 `painted` 缓存跳过重复 `u.blit()`。
- B：J12 只跳过未变的 **fields base**（`ReplicaScene.applyConfirmed`），`VisualPose.apply`、`AuthorityAnimation.apply`、`healthBar` 仍按确认帧执行；J13/J17 的“姿态/插值记录跳过”ABAB 仅约 −2.5%/持平，未部署；J18 的动画帧缓存因 `blank`/visData 处理不完整导致 enemies join 1 项失败，撤销。也就是说，A 的整单位/blit 去重思路在 B 还没有安全落地。
- 影响：加入侧每次确认仍要遍历所有单位姿态/血条；80 敌时 `replica.units` 约 1.3–1.5ms（J12 实测），不是最大头，但可与 fields 跳过叠加。
- 风险：B 的 `VisualPose` 记录/`AuthorityAnimation`/hpbar 嵌套结构比 A 复杂；J18 的失败说明必须把 `visData`/`blank`/子对象身份纳入键，而不是只比较 frame/ID。

### 2.5 host 每 tick 对象链重复遍历（高，但 B 特有）

- A：`UnitPresentation` 每批只建一次 `weaponList/scanBullets` 链索引（`UnitPresentation.as:34-85`），呈现/观察复用；不是每 tick 多份完整场景。
- B：`RoomRuntime.capture` 在同一 tick 可被调用最多 3 次（`RoomRuntime.as:117,154,185`），`SceneSnapshot.capture` 又走一次 `room.firstObj` 链（`SceneSnapshot.as:127-149`）；A 的“单次链索引”是参考，但 B 的 step 前/后/最终状态语义不同，不能简单缓存最后一次。
- 影响：host publish 的大头之一；80 敌/持续射击下对象链与弹丸 state 重复构造会放大 GC 和长帧。
- 风险：必须保留 step 前后/结束事件语义；A 的模型不适用 B 的 host authority，需要 B 自己的 tick 版本化/最终状态合并。

### 2.6 无显示弹丸仍进入 host 记录/发送（中）

- B：`RoomRuntime.projectile`（`:211-228`）对任何 `owner/weap/begx` 对象生成 state，`clip` 为空时仍带 `clip:""` 与 visual/pose 字段进入 `recent/latestByRoom`；`HostSession.projectilesForRoom`（`:167-173`）明确注释 **No visibility culling**；加入侧 `ClientReplica.applyProjectile`（`:266-267`）看到 `clip==""` 直接返回。结果是 host 采集/编码/发送了加入侧不会画的辅助弹丸。
- A 对照：`ProjectileVisuals.capture`（`:27-33`）对 `vis==null` 返回 null，A 的报告把“无显示辅助对象不应反复进入显示记录”作为生命周期优化方向；A 仍可能保留极小的 null 事件，但不会为无显示对象构造完整视觉。
- 影响：爆炸/伤害辅助弹丸密集时，host `RoomRuntime.capture`、`FrameDelta`、wire 都有无效负载；属可测的定向优化。
- 风险：必须保留抓取/爆炸/结束事件和同 tick birth/end；不能简单丢弃所有 `clip==""`。

### 2.7 次要/待验证项

- **A 的 `_lastUnitVisual` 与 `painted` 组合**：建议按 A 的精确条件重试，而不是 J13/J18 的简化版。
- **A 的 UI 文本签名**：B 的 HUD 刷新是固定 100ms，即使不可见也可能计算布局；可先做“不可见/折叠页不刷新 + 文本变化才写”。
- **B 的 ended 池**：`ClientReplica.as:146-163` 保留 240 tick（约 8s），A 是结束记录后约 700ms 退休；B 存的是小对象 id/tick，内存风险不大，暂不作为主项。
- **A 的离线 skip**：B 的 replica/host 只在 welcome/accept 后创建，A 的 `skipOfflinePresentation` 不适用，不应移植。
- **A 的 50ms Timer/200ms unitsync**：A 自己的报告已证明 Timer 合并/抖动不可靠；B 的 `PlaybackClock` 更好，不应回退。

## 3. B 已经比 A 强、不要误当缺口的机制

- `FrameDelta` 路径树/分支复用、`NativeFields`/`VisualPose` 不可变记录与 delta 提示（B 有，A 的 RoomCodec 只是房间检查点稀疏编码）。
- `PlaybackClock` 单房间时钟/自适应缓冲、`Link` 半包游标/批量 drain（B 有，A 的 RemoteMotion/TcpLink 不可直接替代）。
- 只发加入显示房、`ClientReplica` 接收端房过滤（B 有；A 的广播路径反而更宽）。
- 伤害数字静态模板/字体缓存（B 已有 `DecorativeEffects`/`RCLocale`，不要按 A 的 native Emitter 重做）。
- 姿态记录复用/`PoseTween`（B 比 A 完整；J11/J12 进一步降低 decode/apply）。
- 血条：A 是每帧本地 `visDetails` 重算，B 的 `HealthBarPose` 虽 compact 实际 0 命中，但完整同步回退并不比 A 差；不要为了“像 A”恢复 smooth03 compact。

## 4. 建议的 B 侧改进顺序

1. **P0：同房间地形保留**——先写 B 专用 `LocationTerrainCache` 原型，只在“同 key 且非 rebuild/recalc、无 wall/ink dirty、tile inputs 相同”时跳过 `drawLoc`；`loading` 场景加 `terrainReused`/`terrainRedraw` 计数，ABAB 验证恢复/重访帧。参考 A 的 `RoomTerrainView`，但不要复制其对象生命周期。
2. **P1：稳定尸体跳过**——按 A 的 `sost:animState + pending weapon events` 条件，不要冻结记录；只跳过完整 `NativeFields/VisualPose/HealthBarPose` 采集，保留首次死亡态、爆炸、结束事件；用 enemies 死亡阶段 + 真实战斗验证。
3. **P2：UI 文字/字体缓存**——`NetHud.refresh` 值变化才写、`RCLocale.fit` 签名缓存、折叠/不可见页不布局；低风险，先做。
4. **P3：按 A 的 `painted`/`_lastUnitVisual` 精确条件重试整单位视觉/blit 去重**；J13/J18 的简化版失败，不要复用。
5. **P4：host 对象链去重/无显示弹丸过滤**——先加 host 侧计数（`clip==""` 的 state 数、对象链遍历次数）和 ABAB，再决定 tick 缓存/过滤；这是 B 特有收益，但语义风险最高。

## 5. 需要补充的验证

- **A/B 同场景**：目前没有同一环境的新 A/B ABAB；A 的历史数字是组件/生命周期级。若要正式比较，应在同一 11 模组环境分别跑 A 正常入口与 B 可玩包，记录 frame intervals，至少 8/80 敌 ×60s ×2。
- **房间重访/恢复**：`loading`/`textmotion` 场景记录 `terrainRedraw`、`terrainReused`、恢复耗时。
- **尸体/爆炸**：真实 `random_mane` AI/爆炸/死亡/破墙；当前 `enemies` 是真实敌人 AI/武器/伤害，但不是全地图混合场景。
- **UI**：折叠/聊天/设置页切换时的 `TextFormat`/`setTextFormat`/GC 计数。
- 需要接受：A 的 48ms vs 383ms、56→0 等数字是**特定场景/组件级**，不能直接换算成 B 的整场 FPS；A 自身报告也明确没有证明“记录泄漏占全部卡顿比例”。

## 7. 本轮补齐尝试与实际幅度（2026-11-01 更新）

未修改 A；B 安装体已按用户指示从 J12 晋升到 **J12+P1+P3**（`b-p13-01`，`014a7ad8…328`）。

**P0 B 专用渲染地形缓存**：已补齐验证并部署。源 `build/ab/b-p0-source-01`，安装体 `b-p0-06`（`a382e94f…8386`），部署事务 `b-p0-deploy-20261101-01`；旧 P13 体已备份，A 未动。做法是保留最多 2 个房间的 `visFront/visBack/visBack2/visVoda/visSats` 渲染面、轮廓和边框变换；房间标实用选定 style 字段签名，背景 `VisualPose.recipeEqual` 结构比较，tile 值逐项比较。换房先恢复缓存，未命中才 `drawLoc`；只有换房写缓存，同房重绘不承担克隆。功能：textmotion 104/117、rockets 50/50、terrainlive 178/123、enemies 50/50、loading 68/62、ui 127/84、boundary 61/52 全通过。计时：重复房间恢复 **8–13ms**；未命中 `drawLoc` **143–538ms**，首次缓存克隆 **6–141ms**；同房重绘 `storeMs=0`。两轮 P0 vs P13 ABAB 合并 join80 mean 42.59 vs43.04（−2.9%）、P95 70.25 vs74.5（−5.7%）。内存：loading 配对采样 join 稳定私有内存 +35MB，两房间渲染面理论上限约76MB。

**P4 host 对象链去重**：没有实现。`RoomRuntime.capture` 的三次调用分别位于 step 前、step 后、EXIT_FRAME 后，带不同的 step/事件语义；没有安全的 tick 缓存条件前，缓存最后一次会丢失 birth/end/武器事件。

**结论**：P1/P3 已按指示部署为小幅优化；P0 已补齐功能/两轮 ABAB/内存评估并部署，主收益是重复房间地形恢复（8–13ms vs 143–538ms），密集战斗 mean 仅约−2.9%、P95约−5.7%，内存实测 join +35MB；P2 无可分离收益未部署；P4 仍需专门设计。
