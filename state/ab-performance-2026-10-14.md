# A22 / B193 实机试运行与性能对照（2026-10-14）

四轮 A→B→B→A 的实际运行均完成，八个进程测完两档场景后退出。观察结果是：B 的密集场景加入侧更新较快，主侧更新较慢；B 尚不能称为全面提速。**严格负载门禁未全部通过**，原始 `series.json.complete=false`、`comparison.json.comparisonValid=false` 均保留，不能宣传四轮全绿或纯架构因果收益。

## 版本与方法

- A：安装版 0.2.22-dev，原始 SWF `32602e77a21b206d1f7ff0e927b953878c28254e7201529455818923a3539732`。
- B：当前优化候选 B193，原始 SWF `615a82ba6dab43fd4afbc811f48322e4aed5500054c31970cab14c1a6ee4d99c`；原生019 / TDFC004 / RV003 / MSW011 / Sandy001。不是已交付 B190，也未替换它。
- 公共物理基线 `build/ab/baseline-001`，保留其他已冻结模组；B 使用获准的独立接口。两版不可能是完全相同的游戏/接口字节，因此比较的是各自完整运行组合。
- 公共外置驱动 `build/ab/ab-driver-006`，source `5127c21ad22162628f8ca224eb199043625d18e547ed8ead549e0b8f87dd92eb`，manifest `0242f232578f38d8a9c8093f6bd19789509ce018ac57ada4558db98a7e6e583e`。加载原始候选，未把测试代码编入 A/B。B 只替换公开测试 Probe；A 用公开游戏/连接接口。
- 固定 `rbl/loc0_0`，1920×1000，48×25 格；窗口实际内容 984×611，目标30帧。清理原对象、设置同一射击通道，两名角色分别固定在 (250,879)、(330,879)。两版均记录实际位置、生命和敌人显示对象数。
- 每轮8尸鬼、80尸鬼两档，各预热5秒、测量45秒。实际原生单位/AI/动画/子弹/联机保留。角色、敌人保护以防死亡改变负载；不测试伤害平衡。LMG等级/技能、满90发弹匣、10000备用弹一致；每3秒按住2.5秒、松开0.5秒，保留原生换弹/耗弹，修复武器耐久并禁随机卡壳。
- A 每帧尊重原生消费射击键，下一次明确松开/按下才恢复；B 发送相同时间规则的动作输入。帧率不同会改变实际模拟与射击进度，这本身是游玩差异，不做强制补帧/补射掩盖它。
- 所有轮次使用默认 Windows 调度；不设置旧 A 工具的 HighQoS，不操作其他用户程序。测量期间未编译，归档在轮次之间运行。
- 每个新实例使用独立 AppID/Local Store，没有读取/修改用户角色档。只结束自己启动的进程。
- 指标：同一 Stage ENTER_FRAME 观察器的帧间隔，非 GPU 实际呈现计时；消息往返为应用层 socket echo，非端到端动作延迟。内存为 AIR 堆，非整进程工作集。没有模拟公网。

下表保留四轮原始观察；末轮 A 的加入侧连续耗弹门禁有一项失败，不能算全部合格的严格等负载性能实验。

|---|---:|---:|---:|---:|
| 01-A | 23.54 / 68 | 28.87 / 50 | 14.42 / 110 | 13.62 / 107 |

P95 是95%的帧间隔不超过该值，越低越好，不是“最低帧率”。80敌人时，超过100ms的帧：A主侧6.38–7.55%、加入侧8.21–8.32%；B主侧31.91–36.21%、加入侧2.91–2.98%。B将更多负担集中到主侧的表现明显，但不能据本试验唯一分解每个模块成本。

密集场景 AIR 堆中位数：A主侧290.0–291.2MiB、加入侧277.0–277.6MiB；B主侧309.2–309.6MiB、加入侧313.2–316.0MiB。短测不证明长期无泄漏。

B密集场景的主侧确认推进约10.3–10.4步/秒，加入侧显示16.4–16.8帧/秒；加入侧播放缓冲记录为195–250ms，队列峰值3，测量窗口内新增欠帧0。**显示更快不等于世界推进更快，也不等于零操作延迟**。缓冲值是内部播放参数，不是实测完整输入到画面的延迟。

应用层往返中位数：密集 A 主侧71–107.5ms、加入侧63–89.5ms；B主侧107.5–127ms、加入侧113–117ms。这里包括两侧单线程调度和收发处理，不能当公网 ping。

真实扣弹（8敌人 / 80敌人）：A01主357/182、加391/212；B02主270/168、远端270/168；B03主270/174、远端270/170；A04主360/237、加450/193。B加入侧库存显示与主侧实际远端库存接近，末次快照可相差少数发，不声称零帧误差。

## 资格限制与发现

1. **A04加入侧密集窗口触发“五个采样间隔必须继续耗弹”门禁。** 总弹量在15.581–20.745秒停在9550，21.755秒降到9545，此后持续射击；37.260–41.389秒停在9460，42.435秒再次减少。都是90发弹匣边界，符合换弹特征。原生LMG定义 `AllData.as:2725` 为60步换弹，`Weapon.step`按模拟步递减；在约13.5帧时固定5秒检查可能太严。但本夹具未记录 `t_reload`，不能逐次确认具体停顿原因，**没有修改旧门禁或把失败改写为通过**。下一轮记录弹匣/备用弹/换弹计时/输入边沿，再按原生过程判定持续射击。
2. **A两轮均在开场地图同步记录 Area 构造 #1063。** `obj spawn 'null' failed: Argument count mismatch on fe.loc::Area(). Expected 1, got 6.` 位于初始 begin 地图、正式测量之前；随后成功到rbl并完成双档。登记为 A 现存功能问题，不把它隐藏在帧率结论里，也未在本轮修复。
3. **B两轮加入侧各有一条清理导致的 `peer closed` FATAL/FAIL。** B02公共夹具done=129160ms，关闭日志130153ms；B03 done=130121ms，关闭日志130316ms。发生在两侧测量/截图结束后、runner按持有句柄先结束host时。外置 ABBProbe 没有将原生 `probe.finished` 同时置位，导致原生产收尾把断开记录成错误。不是测量中崩溃，但原日志保留；未来驱动需明确测试结束协议，不能过滤所有断线错误。
4. **绘制负载并不逐帧相同。** 双侧两档的敌人身份/挂载显示对象始终8/80，但主侧80敌人的 `vis.visible`：A约68–80，B约35–44；加入侧均80。截图确认两版视野/前景遮挡和敌人分布不同。相同初始几何、武器和输入不保证原生AI随机轨迹与视野裁剪一致。本次只能提供实际组合的运行参考，不能宣称严格相同像素/AI工作的纯架构速度比。
5. **后台负载在变。** 四轮全运行期系统CPU中位数约67.8%、47.1%、53.7%、54.0%；可用物理内存最低约6.0、5.3、5.3、4.9GiB。启动前可用提交额度均过6GiB门槛，A04运行中最低约5.45GiB。未关闭或调整用户程序。交替顺序缓解顺序偏差，不消除环境波动。
6. 不是完整游玩验收：没有本轮覆盖分房、SATS、念力、特殊武器、死亡重访、真人输入和长局。B190旧完整回归或B193旧专项没有混算成本轮结果。

## 判断与接续

现阶段B更接近“加入侧呈现更轻、主侧承担更多”，不能作为全面性能升级替换A。下一步先补足共同驱动的换弹状态记录和正常收尾，再分开测“相同可见对象的固定显示回放”与“正常AI战斗”，分别解释纯同步成本和真实玩法差异。B优化优先关注主侧完整一帧的处理和确认到呈现的等待；不能为了帧率砍掉敌人、武器/效果或改变伤害规则。A的Area构造问题单独登记待查。

当前没有自有测试进程；A安装版、B190独立入口、B193生产源均未改动。
